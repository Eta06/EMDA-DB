# Lifecycle of unmarked legacy staging paths

Older versions may leave names beginning `.db-backup-`, `.db-restore-`, `.db-upgrade-`, `.db-index-` or `.db-compact-`. A matching name does not establish ownership, completion, redundancy or even that the path was created by this engine. It can contain the only usable copy of data. The engine **never automatically deletes these unmarked paths**, and `cleanup_abandoned_staging` deliberately ignores them. The default lifecycle is indefinite retention for operator review; age, apparent contents and name alone are insufficient grounds for removal. The current marked-stage cleanup has separate ownership and trusted-directory assumptions described in the storage contract.

When an operator needs to investigate such a path, use a trusted maintenance environment and keep the original intact until its role and a separately protected copy have been verified:

1. Identify the parent filesystem, application and every process that could use it, including older engine versions and children that inherited descriptors. Stop or otherwise coordinate all relevant writers, maintenance workers and consumers. A current-version advisory directory lock alone does not prove that older or noncooperating processes are idle. If coordination or ownership is uncertain, leave the path in place.
2. Record the exact path, entry type and metadata without following symlinks. Treat symlinks, unexpected entries and names containing control characters as untrusted; do not traverse or delete them as part of a generic cleanup. Preserve evidence of any publication or synchronization error, since its outcome can be uncertain.
3. Preserve the candidate and any live source, destination, witness and related metadata in separate protected copies. Inspect only a detached copy with the appropriate format/version tools: opening a writable store or restoring it can create lock files, synchronize or adopt an unacknowledged tail, and therefore is not a read-only inspection of the original. A file that parses or has a valid checksum is not authenticated, complete, or necessarily the latest copy. Reconcile successful acknowledgements and intended destination with independent operational records.
4. Retain the original until an authorized operator has determined it is redundant and established a retention policy. If it remains uncertain, retain it indefinitely. A manually managed quarantine or deletion requires the same offline coordination, trusted paths, a separately verified recovery copy, and appropriate same-filesystem non-overwriting rename and directory synchronization where durability matters. An error or interruption during a move can leave an uncertain result; inspect both locations and keep all copies until resolved. Do not assume a generic recursive delete is safe.

No automatic quota recovery, secure erasure, off-host restore or physical-power-loss validation is provided by this policy. The currently testable cleanup behavior preserves representative legacy files, directories and symlinks; it cannot prove that an operator's specific path is redundant or recoverable. A future service may add explicit ownership and retention metadata, but must not infer it retroactively from these names.
