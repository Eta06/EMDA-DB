# Storage engine architecture

This document describes the current prototype, not a promised final design. The product and package names are placeholders. See the [storage and transaction contract](STORAGE_TRANSACTION_CONTRACT.md) for current behavior, proposed guarantees, and the rule that performance optimizations must not violate durability, isolation, or recovery guarantees.

## Boundaries

- `store` and `store/commit`: public key/value API, exclusive process ownership, bounded group commit, synchronization, and outcome handling.
- `record`: versioned binary framing, length limits, encoding, and checksum verification.
- `log`, `log_io`, `recovery`, and `witness`: append and sync, positional reads, bounded buffered replay, the checksummed commit boundary, the in-memory key-to-offset index, and testable I/O boundaries.
- `backup`: checksummed full-log backup and validated, non-overwriting restore.
- `checkpoint`: explicit persisted index snapshots bound to a separately trusted digest and witnessed log prefix; opening still hashes the full covered prefix.
- `checkpoint_view`: a shared-lock, bounded-memory reader of a verified historical index; it does not validate or replay later log records and cannot coexist with a cooperating writable store.
- `recovered_view` and `checkpoint_store`: merge a validated, bounded witnessed suffix with the verified checkpoint. The former is read-only; the latter takes an exclusive lock and serializes synchronized mutations, but has no transactions, snapshots, group commit or automatic checkpoint rollover.
- `directory`: synchronization of created store paths and their ancestors.
- `tests`: behavior across reopen, deterministic I/O failures, concurrent clients, corruption, backups, and process termination.

The ordinary `Store` API supports `put`, `get`, and `delete` on nonempty byte keys and backup/restore. Values may be empty. Its commit coordinator reserves bounded capacity before preparing a write outside the queue lock. It queues prepared records, appends each batch in queue order, synchronizes the log, and only then publishes index changes and returns success. Multi-record batches use vectored writes when the I/O implementation supports them, with a sequential fallback. A batch contains at most 64 records; admission limits reserved and queued encoded bytes and record count. A reader locks the index to select an immutable log location, then releases the lock before reading and verifying the value. A separate barrier makes backups wait for in-flight writes and prevents new writes during the copy. Completed writers are woken individually; queued writers periodically recheck leadership if a handoff is delayed. This does not provide a bound on scheduling or request latency. Grouping independent mutations does not provide multi-key transactions. An I/O error or leader panic leaves unacknowledged outcomes uncertain and makes that store instance refuse further operations until it is reopened.

## Log format

Records use a four-byte `DB01` magic/version, one-byte operation, little-endian 32-bit key and value lengths, a CRC32 of the header fields, the key and value bytes, and a CRC32 of the header and payload. New Linux stores use `EMDALOG3` when user xattrs are supported: a checksummed boundary lives in the log inode's `user.db.commit.v3` xattr. One full inode `fsync` covers the records and boundary before index publication or acknowledgement. An immutable `commit.state` identity anchor detects missing or substituted log headers. The boundary is outside the log bytes, preserving detection of log-only truncation/rollback below the boundary. Before sync completes, either records or metadata can persist first; a boundary ahead of complete valid data fails closed. Existing V2 (`EMDALOG2`) stores and creation on unsupported filesystems keep the separate witness and two ordered syncs. Missing or unsupported V3 metadata is an error, never a downgrade. No format guarantees protection against combined rollback of data and witness. [Format details and upgrade rules](VERSIONING.md) describe the filesystem requirements. A preserved witness detects truncation before its recorded record boundary. Recovery reads the log sequentially through a buffer of at most 64 KiB, validates full records, and reconstructs the index in order. A complete tail beyond the witness is synchronized and adopted; an incomplete tail, invalid header, or checksum error fails opening without truncating the log. Legacy unwrapped logs remain supported without the new boundary guarantee. CRC32 detects accidental corruption; it does not prevent tampering or repair lost data.

Atomic write batches are encoded as a single `DB02` record containing checksummed `DB01` child operations; all child index updates are published under one index lock after the commit witness is synchronized. Read-modify-write transactions capture a bounded index snapshot and the in-process commit generation, stage writes, and validate under the exclusive write barrier before committing one atomic batch. The default mode conflicts on any intervening mutation; an opt-in read-set mode checks observed points and complete scan ranges against the current index. Callback errors discard staged writes. The callback runs without the writer lock and is never automatically retried. Earlier software cannot read `DB02`; see the versioning policy.

The ordinary store's index keeps keys, offsets, lengths, and value checksums in memory and is not bounded. The experimental checkpoint-backed store keeps its base index on disk and bounds the suffix overlay, but its limits are not total-memory guarantees. It can stream a new checkpoint and reopen with it to clear the overlay; this is not automatic, and unacknowledged-tail recovery still requires the ordinary store. Values are read by offset and verified. The live log grows without automatic compaction; a verified separate compacted copy can be created without modifying the source. Recovery scans or hashes the complete log prefix. The directory lock is advisory and assumes cooperating processes and a suitable filesystem. Store initialization synchronizes the created directory path and its ancestors; this does not prove power-loss behavior on all filesystems. Successful `sync_data` is not a guarantee against faulty hardware or filesystem behavior. Tests that kill a process do not simulate a power failure.

Backups copy the full log while writes are blocked, include a SHA-256 digest and length, verify record checksums, and publish without overwriting an existing path. The full log retains old and deleted values; a delete is a tombstone, not secure erasure. Restore validates a backup, rechecks the copied data and record checksums in a staging directory, and publishes the new directory without replacing an existing path. Neither digest nor CRC authenticates data, and backups are not encrypted. Publication followed by a directory-sync error has an uncertain outcome. Only Linux has been tested; platform and filesystem behavior remain assumptions. Backups should be stored independently and restored in drills before relying on them.

## Next boundaries to design

Expand transaction isolation and conflict testing, and design an on-disk index, live compaction, cache management, broader fault injection, and power-loss validation. A worker lifecycle for project sleep/wake and a network API would be separate components from this embedded engine. SQL, documents, and secondary indexes require explicit semantics; they are not implemented by exposing the current byte API.

Consider Rust SIMD or assembly only after profiling shows an end-to-end benefit. Optimized paths must retain a portable implementation, detect CPU support safely, and pass the same correctness and corruption tests.
