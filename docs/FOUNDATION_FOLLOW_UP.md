# Foundation and storage follow-up

This is the handoff for work remaining from roadmap priorities 0 and 1. It is a checklist, not a statement that the prototype is production-ready. Update it when work is completed, and link the relevant implementation and evidence.

## Deferred to later Codex sessions

- [ ] Physical power-loss validation on explicitly identified disposable hardware. Define the filesystem, storage device and failure procedure; check acknowledged writes, metadata witness behavior, recovery and preserved evidence. A process kill is not a physical power failure. Do not perform destructive testing on a production server.
- [ ] Off-host backup and restore drill on an independently identified target. Verify restored content and report transfer, filesystem, failure and isolation assumptions. A separate directory or filesystem on the same VM is not an off-host drill.

## Priority 0: remaining local foundation work

- [ ] Expand interruption and failure injection across initialization, commit, backup, restore, upgrade and every directory-sync boundary. Record which persistence states the model covers and does not cover.
- [x] Exercise process termination during synchronized compaction staging and after publication before parent-directory sync. The latter establishes only what remains visible on the running OS, not what survives a physical power failure.
- [x] Explicitly release privately owned compaction staging-store locks before reopening or publication; a duplicated descriptor regression test and repeated release-suite runs cover the handoff.
- [x] Exercise process termination after backup and restore staging is synchronized and immediately after their publication. Verify the source/backup and the resulting copy or retry on the still-running OS; physical power failure remains untested.
- [x] Exercise process termination at upgrade staging and publication for persistent V2 and V3 sources, and inject parent-directory sync failure. These process-level tests do not establish power-loss safety.
- [x] Exercise process termination at checkpoint staging and publication, including cooperative cleanup while the operation is active and after it exits. This is not a physical power-loss test.
- [x] Define and test the supported fork/exec lifecycle for long-lived store and checkpoint-view locks. On tested Linux, process checks confirm that an inherited descriptor retains the lock after its original owner drops and releases it on `exec`; separately executed contenders are excluded while the owner is active. A child must not use an inherited store/view after `fork`; arbitrary external descriptor manipulation is unsupported.
- [x] Add a persistent V3 fixture covering ordinary records, an atomic batch, deletion and a transaction. Verify opening without rewriting the fixture, subsequent writes and rejection of missing/corrupt metadata.
- [ ] Extend concurrent history and recovery testing beyond the current short histories. A 2,048-iteration model check mixes ten concurrent operations on the ordinary store: conservative, read-set and FIFO transactions with and without unexpired deadlines, atomic batches, independent writes and bulk reads, with a reopen after every iteration. Half of those histories use live-key count and byte caps. A separate 256-history checkpoint-store test checks two transactions, a blind batch and a bulk read against real-time-compatible serial orders and verifies every result after full recovery. These tests do not cover deadline races or exhaust all histories. Add persistent fixtures for future supported format versions.
- [ ] Extend recovery fuzzing with additional targets, malformed inputs, longer campaigns and replayable regression cases. The 363,780-input local recovery run is recorded in `benchmarks/results/2026-11-04-foundation-fuzz.json`; the historical checkpoint reader was included in `benchmarks/results/2026-11-03-checkpoint-view-fuzz.json`, and interleaved read-set histories in `benchmarks/results/2026-11-03-read-set-fuzz.json`. A further 18,084-input [model run](../benchmarks/results/2026-11-04-deadline-fuzz.json) includes deadline-enabled modes with unexpired deadlines; it does not model deadline races. The [recovered-view and replay-parser runs](../benchmarks/results/2026-11-04-recovered-view-fuzz.json) exercised 78,981 and 132,364 inputs respectively. These runs are not exhaustive.
- [ ] Measure memory, I/O and recovery behavior under workloads representative of the intended deployment, including large data and repeated restarts. Existing local point-operation comparisons are a baseline, not a comprehensive performance ranking.
- [ ] Keep write acknowledgement, unknown outcomes, corruption handling and compatibility limitations aligned with `STORAGE_TRANSACTION_CONTRACT.md` as behavior changes.

## Priority 1: durable storage and core operations

- [x] Add an explicit on-disk index checkpoint verified against a separately trusted digest and suffix replay, with historical peak accounting and fail-closed corruption/format checks. The checkpoint is a derived plaintext file, not a backup or a security boundary when its digest is attacker-controlled.
- [x] Add a bounded-memory historical checkpoint reader with per-block integrity checks and a shared store lock. It does not validate or replay the later log tail and is not a live writable index.
- [x] Add a read-only recovered checkpoint view that validates a bounded witnessed suffix and merges its key overlay with checkpoint point reads and scans. It rejects unacknowledged tails and holds a shared lock excluding cooperating writers; prefix hashing and total process memory remain unbounded.
- [x] Add an experimental writable checkpoint-backed store with a bounded suffix overlay, synchronized single-key and atomic batch writes, conditional updates and ordered scans. Capacity rejections precede append; V2 partial append/witness, V3 metadata fault and process-kill tests check fail-closed recovery. A short [model fuzz run](../benchmarks/results/2026-11-04-checkpoint-store-fuzz.json) checks repeated recovery and limit enforcement. It has no snapshots, group commit or automatic checkpoint rollover.
- [x] Stream an explicit new checkpoint from the verified on-disk base and bounded suffix, preserving historical key-count peaks and checking the output before publication. `rollover_to` switches the open store while retaining its exclusive lock and clears the overlay; the digest and checkpoint selection remain external. Rollover blocks reads and writes, and publication-sync errors have uncertain outcomes. A [model fuzz run](../benchmarks/results/2026-11-04-checkpoint-rollover-fuzz.json) checks the streamed checkpoint and historical peak against ordinary recovery.
- [x] Validate and synchronize complete unacknowledged tails during checkpoint-store recovery without loading the full index, within the suffix limits. Partial single and batch records, invalid witness boundaries, V2 witness failures and V3 metadata failures are checked; sync failures have uncertain outcomes.
- [x] Add full-log backup to the checkpoint-backed store and stream record validation during backup, restore and format upgrade without materializing a full key index. Backup blocks mutations, checks all records, and restores into a separate store; opening that ordinary store still loads its index. The [V2/V3 bounded-recovery fuzz run](../benchmarks/results/2026-11-04-checkpoint-recovery-fuzz.json) exercised 18,619 inputs; a [backup-restore fuzz run](../benchmarks/results/2026-11-04-backup-restore-fuzz.json) exercised 21,685 inputs.
- [ ] Complete the live disk-backed index and bounded memory/cache management. Suffixes exceeding the selected caps need a newer checkpoint or ordinary recovery, and all checkpoint openings hash the complete covered log prefix. Overlay limits are not total process-memory limits.
- [x] Add verified, non-overwriting compaction into a separate store while keeping the source intact and blocking concurrent mutations during the copy. Bounded groups of ordinary records synchronize before verification and publication; append, sync and pre-publication failure paths are tested.
- [x] Add separate-copy compaction for the checkpoint-backed store, streaming the verified source index and target validation and producing a checkpoint with a separately trusted digest. Tests cover corrupt staging data, process termination at staging and publication, and source mutation exclusion. A short [model fuzz run](../benchmarks/results/2026-11-04-checkpoint-compaction-fuzz.json) exercised 8,416 inputs; its binary hash was not retained. This is not a total-memory or power-loss guarantee.
- [ ] Design and implement automatic checkpoints, live/online compaction, garbage collection and bounded recovery. Explicit index checkpoints still hash the full covered prefix. Protect readers and snapshots during reclamation. Separate-copy compaction requires manual switchover and does not include later source writes; the ordinary-store compactor still builds multiple in-memory indexes.
- [x] Add explicit cleanup for new versioned staging markers and payloads from backup, restore, upgrade, checkpoint and compaction in a trusted parent directory. A shared/exclusive advisory directory lock coordinates cooperating new operations; cleanup skips unrecognized markers and symlink payloads and synchronizes the directory. Process-kill tests cover staging and publication boundaries, but do not establish power-loss behavior.
- [ ] Define lifecycle management for older unmarked `.db-backup-*`, `.db-restore-*`, `.db-upgrade-*`, `.db-index-*` and `.db-compact-*` paths; they cannot be safely identified for automatic deletion by their names alone. New cleanup is opt-in, depends on filesystem lock/sync behavior and trusted cooperative directory access, and is not secure erasure or an automatic service.
- [x] Add initial bytewise ordered scans with exclusive bounds and pagination. Each page is limited to 1,024 entries and 32 MiB of key/value data; ordinary scan pages can see changes. Continue until an empty page; a byte-limited page can be short.
- [x] Add single-key compare-exchange for conditional put/delete, synchronized on success and serialized against mutations; it does not detect ABA changes or provide multi-key transactions.
- [x] Add signed 64-bit atomic increment with checked overflow and specified byte encoding; it is serialized against mutations.
- [x] Add bounded multi-key reads from one captured index state, preserving input order and missing keys. This is not a multi-key transaction.
- [x] Provide the same bounded multi-key read semantics on the checkpoint-backed store, with concurrent batch-visibility and response-limit tests.
- [x] Implement bounded atomic multi-key write batches as single synchronized DB02 records, including failure, crash-state, format-compatibility and recovery checks. DB02 records are unreadable by earlier revisions; batch writes require witnessed stores.
- [ ] Profile and reduce compare-exchange/increment/batch contention without weakening their semantics; they currently exclude all concurrent writers, including writers to other keys.
- [x] Implement a bounded optimistic serializable read-modify-write transaction prototype, including point/range reads, read-your-writes, rollback on callback error, conservative store-wide conflict detection and atomic DB02 commit. Independent operations and group commit are not transactions.
- [x] Add bounded point-conditional atomic batches to the checkpoint-backed store, including concurrent transfer, validation, quota and uncertain-commit tests. A short [reference-model run](../benchmarks/results/2026-11-04-checkpoint-conditional-fuzz.json) exercised 10,251 inputs. This primitive compares current values, does not detect ABA or validate ranges, and is not a general transaction callback.
- [x] Add conservative optimistic transactions to the checkpoint-backed store without copying its full index. Each read and final commit checks a process-local generation; staged writes commit as one DB02 record. Tests cover conflicts, range scans, ABA, transfers, resource reservations, rollover, process termination after acknowledgement and uncertain commit failures. This mode conflicts on all intervening writes and provides no deadlines or read-set validation.
- [x] Bound the aggregate encoded staged-record bytes held by concurrent transactions on one open store, with admission before staging and cleanup on completion or unwind. This is not a total-memory or cross-store quota.
- [x] Add opt-in bounded read-set validation that allows unrelated writes while preserving serializable point and range observations. The default transaction mode retains its store-wide conflict rule.
- [x] Add optional FIFO commit admission among callers that select it, with bounded queue and failure/panic wake-up tests, including delayed synchronization failure and panic while another transaction is queued. Other transaction modes and independent writes are outside the queue; there is no wait-time guarantee.
- [x] Add optional operation-boundary deadlines for all transaction modes, including timed FIFO queue removal and a distinct pre-commit expiry result. Tests verify expiry while waiting for the writer, successful synchronization finishing after expiry, and a synchronization timeout retaining an unknown outcome.
- [ ] Extend transaction model checking, fault campaigns, benchmarks and resource limits. Both validation modes require a bounded full-index snapshot and do not automatically retry callbacks; read-set validation compares complete ranges while holding the writer barrier and does not provide absence-version tracking. A small [SQLite comparison](BENCHMARKS.md#two-key-transaction-comparison) found high prototype p99 under eight clients despite no disjoint read-set conflicts. Optional FIFO reduced that sampled tail at the cost of higher median latency and, for shared keys, many more retries; investigate admission and compare equivalent transactional workloads with PostgreSQL and other suitable engines.
- [x] Add bounded, process-local read-only snapshots with stable paginated scans; each snapshot is released on drop and borrows the store.
- [x] Add per-store aggregate limits for active snapshots, copied key count and copied key bytes; release reservations on drop.
- [x] Add explicit read-only snapshot cancellation and optional operation-boundary deadlines; cancellation releases the copied index and reservation and expired reads fail.
- [x] Reclaim expired, idle snapshot views on later snapshot admission or an explicit reaping call, without interrupting in-progress reads. Busy views are skipped.
- [ ] Add any desired idle-time reclamation policy, explicit transaction cancellation, interruptible admission and safe live-log reclamation compatible with all snapshot lifetimes. There is no snapshot reaper thread; idle expired snapshots can retain resources. Transaction deadlines do not interrupt callbacks, writer-lock waits or I/O and are not bounded-completion guarantees. Snapshot counters are not total process-memory or cross-store quotas.
- [ ] Add configurable request/connection limits, fair overload handling and cancellation/timeouts without violating unknown-outcome semantics. The current embedded API does not include a production server.
- [x] Add an optional per-open log-file length cap with concurrency-safe admission, rejection before replay and unknown-outcome handling.
- [x] Apply an optional whole-log byte cap to the checkpoint-backed store before replay, unacknowledged-tail adoption and serialized writes. Checkpoint rollover does not reclaim the old log; the cap is not a persistent or project-wide quota.
- [x] Reserve log space for in-flight records before group commit, allowing independent log-capped writes to share synchronization without exceeding the cap. Rejected preparation releases its reservation; uncertain commit failures poison the store and recovery recounts the log. A short [8,498-input model fuzz run](../benchmarks/results/2026-11-04-log-limit-fuzz.json) checks record lengths, rejected writes and reopening.
- [x] Add an optional per-open live-key count limit, allowing existing-key updates and freeing slots after deletions, with serialized admission for membership changes. Enforce it during recovery for every historical prefix; a historical peak can require compaction into a separate copy before opening under a lower cap.
- [x] Add an optional per-open live-key byte limit with serialized membership changes, constant-time counter updates, ordered batch admission and recovery checks at every historical state. Fault tests reopen after uncertain writes, and a short [12,102-input model fuzz run](../benchmarks/results/2026-11-04-key-byte-limit-fuzz.json) checks repeated reopening and rejected writes. This logical limit excludes index overhead, values, snapshots and total memory, and is unavailable with checkpoint recovery because checkpoints lack the historical byte peak.
- [x] Allow updates to already-present keys under the count/byte caps to share synchronization. A shared write barrier prevents concurrent membership changes; grouped sync failure and panic tests fail closed and preserve quota accounting. A configured log cap reserves space for each in-flight record.
- [ ] Enforce persistent project-wide memory and storage quotas, including other files, recovery and background work; scan response limits and the per-open log cap do not bound total store memory or total disk usage. Membership-changing writes under key caps still serialize and need further measurement and optimization without oversubscription.
- [ ] Demonstrate the priority's exit criteria: independent concurrent clients, transactional atomicity, acknowledged-write recovery under the documented fault model, and measured memory within configured limits.

No optimization may weaken the durability, isolation or recovery guarantees in force. Preserve failures and unresolved gaps in reports rather than marking them complete without evidence.
