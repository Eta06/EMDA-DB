# Incremental collection deletion: local validation

Incremental collection deletion uses an irreversible version 3 metadata marker, blocks normal access to the affected collection, and removes at most 128 document or index keys per atomic step. Callers schedule further steps after reopen or a retryable conflict. The final empty step deletes the marker and collection metadata. Finish or cancel schema maintenance and finish index maintenance, including cancellation cleanup, before starting. A commit I/O failure has the underlying unknown-outcome semantics; the caller must reopen and inspect status rather than assuming a rollback. The [document model](DOCUMENT_MODEL.md#resumable-collection-deletion) describes limits and compatibility.

The full stable all-target suite passed 831 tests at `4de3c42`, including both writable backends, a collection with 810 data/index keys, reopen and full-log recovery, aborts, neighbor preservation, name reuse and an in-flight read-set writer conflicting with the marker. Additional checks reject invalid marker/version combinations and test V3 witness failures while starting deletion and completing its final step. Rust 1.85 passed the four integration tests. Stable all-target Clippy and 48 Python workflow tests passed.

At `a7c4f01`, the [local stress campaign](../benchmarks/results/2026-11-05-collection-drop-stress.json) ran six tests 20 times each on tmpfs and the workspace overlay: 240 successful invocations. These included 105 byte-cut positions per interrupted deletion-step append plus three injected append panics per run, and seven V3 witness read, write, synchronization and panic cases per run. When reopen succeeded, the test checked that the step and a raw-key receipt appeared together or neither appeared; on a fail-closed reopen it checked the log bytes remained unchanged. An initial test incorrectly injected log synchronization faults on V3's metadata-witness path, where they were not reached; it was corrected to inject witness failures and then passed. The overlay backing device was not independently verified. These running-VM checks are not a physical power-loss or off-host restore test.

Three address-sanitized [reference-model campaigns](../benchmarks/results/2026-11-05-collection-drop-fuzz.json) exercised 16,864 small serial histories over both backends, including starting, advancing, aborting, reopening and recreating collections. They do not exhaust concurrent schedules, corruption or power-loss states. The target and seeds are part of the GitHub fuzz workflow. No performance comparison was performed; in particular, checkpoint overlay tombstones can increase repeated scan work. The ordinary store still requires a bounded full-index transaction snapshot, and checkpoint stores may need rollover as their suffix fills. None of this establishes total-memory, latency or project-isolation guarantees.
