# Transaction submission boundaries

Revision `0158359cbc690df1a8144800a8ff966c6e2bd8e0` refines the opt-in transaction outcome classification on both writable stores and the document interface. Configured log-length, live-key and checkpoint suffix limits can return `Rejected` before this transaction submits its staged writes. The ordinary path switches to `OutcomeUnknown` immediately before entering the commit coordinator; it can therefore still conservatively classify a coordinator rejection that happened before append as unknown. The checkpoint path switches immediately before attempting append. This classification says nothing about independent callback writes or automatic checkpoint maintenance, which can have their own side effects or uncertain outcome. No synchronization or recovery requirement was removed.

Focused tests cover log quotas on both stores and both document adapters, live-key and suffix quotas, conservative ordinary coordinator rejection, append and witness failures, cancellation races and automatic checkpoint maintenance. A two-thread test stages two transactions before allowing either to compete for one remaining key; exactly one succeeds and the other is rejected on each backend. It passed 25 repetitions per backend, followed by reopen checks.

## Failure and recovery evidence

The [EAGAIN](../benchmarks/results/2026-11-14-submit-eagain.json.gz), [EIO](../benchmarks/results/2026-11-14-submit-eio.json.gz) and [EINTR](../benchmarks/results/2026-11-14-submit-eintr.json.gz) campaigns exercised 160 selected concurrent syscall-injection cases across V2/V3, both writable paths and both recovery orders. EAGAIN produced 97 acknowledged writes, 192 confirmed pre-submission aborts and 64 unknown outcomes; EIO produced 109 acknowledgements, 192 confirmed aborts and 64 unknown outcomes. All 384 confirmed aborts stayed absent after recovery, and all 128 unknown transactions were recovered completely. EINTR was retried in the sampled cases, with 8,192 writes acknowledged. The reports can be independently checked with `scripts/verify_concurrent_eio_results.py`.

Two optimized mixed-operation runs checked 4,096 histories each on the workspace overlay and on tmpfs; the [logs](../benchmarks/results/2026-11-14-submit-history.log.gz) and [tmpfs log](../benchmarks/results/2026-11-14-submit-tmpfs-history.log.gz) retain counts. Ten repetitions of a concurrent process-kill workload checked 160 cases and 8,839 observed acknowledgements through both recovery paths; all cases reopened. The [process-kill report](../benchmarks/results/2026-11-14-submit-kill.json.gz) includes the receipts. These tests sample schedules with the OS running; they do not establish physical power-loss behavior or off-host recovery.

The stable debug suite passed 948 tests, and the optimized suite and Rust 1.85 rerun each passed 949 tests on the same production code. The final bounded quota-race test was also checked separately on both toolchains; stable and Rust 1.85 all-target Clippy passed. An [earlier Rust 1.85 parallel run](../benchmarks/results/2026-11-14-submit-initial-msrv-failure.log.gz) failed when an unrelated read test immediately reopened a private fixture and received `WouldBlock`. This is consistent with the transient lock contention the existing test helper handles, but the precise source was not established. The test now uses that bounded helper for the reopen; the rerun passed. Intentional lock-exclusion checks still use the direct open call.

## Local performance checks

The [paired transaction comparison](../benchmarks/results/2026-11-14-submit-transaction-pair.json.gz) used clean baseline `9d09dc3a7bfa28068b53d84175853c1058945f18` and the candidate revision above, separate release binaries, alternating order, V3 synchronization and fresh, verified two-key transactions. It covered 96 runs: disjoint and shared keys, one and four clients, four modes, 200 transactions per client and three rounds. Median latencies varied in both directions; it does not establish a general improvement or regression.

The [direct-write comparison](../benchmarks/results/2026-11-14-submit-direct-pair.json.gz) and its [longer repeat](../benchmarks/results/2026-11-14-submit-direct-repeat.json.gz) compared the same revisions using direct writes with a per-open log cap, fresh fixtures and checked reopening. Each has 48 runs across one and four clients, 50% and 100% writes, and four rounds. The first four-client mixed workload measured median 19,244 versus 15,722 operations/s and write p50 351.6 versus 389.8 µs. With 1,000 rather than 200 operations per client, the repeat measured 19,843 versus 20,148 operations/s and write p50 345.0 versus 355.5 µs. Other cases also varied. The first comparison observed up to 4.65% VM steal and 16.67% I/O wait; the repeat observed up to 2.99% steal and 15.38% I/O wait, with no cgroup throttling observed in either. Telemetry covers the whole VM/cgroup including the workload. These warm-cache local samples do not establish production latency or competitor rankings.
