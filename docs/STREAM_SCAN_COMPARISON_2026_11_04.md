# Streaming document scan comparison, 2026-11-04

A collection query previously retained every decoded document until the scan finished. The candidate filters while scanning and, when no sort is requested, retains only the requested result window. It still scans and validates the complete bounded range, applies the same candidate and encoded-byte limits, evaluates predicates for every document in a successful query, and reports a later scan or corruption error before an earlier filter or sort error. Sorted queries retain their matching documents. This reduces one source of retained values; it is not a total-memory guarantee.

We compared the prior code at `c4684dd44601667b90ad0e20a1c2863186a23104` with candidate `56a438c5c1f643a3829883b79ce4a07d636e1d23` using the [partial-index comparison](PARTIAL_QUERY_COMPARISON_2026_11_04.md), including both prototype query paths and SQLite's forced partial-index and primary-table plans. The candidate was later combined with checkpoint admission limits; these timings predate that merge. Every returned result and both databases' complete reopened contents were verified. Both engines ran inside one process with one client; SQLite and the prototype use different APIs and internal validation.

Each series ran before/after/after/before. Each side used four fresh data sets per case with 10 warmup and 50 measured cycles per variant. Numbers are microseconds: the median of four run medians, followed by the range of those medians. The SQLite index column is from the candidate runs and is shown for context, not as an identical implementation.

The repeat's 1,000-document, 10-match scan median was about 20% lower, and the planned median about 25% lower. SQLite's index remained faster on these cases. Earlier partial-index measurements showed a strong dependence on which variant ran first; the raw samples here also retain execution order and the prior run ranges. These small, hot, single-client workloads do not establish production latency, write throughput, cold-cache behavior or competitor rankings. Peak RSS in these files includes both engines and setup; it cannot establish the prototype's independent memory savings.

All 24 primary pre-run quiet checks passed; 23 of 24 passed in the repeat. Across process windows, primary VM steal reached 11.36% and I/O wait 19.53%; the repeat reached 5.56% and 6.67%. No cgroup throttling or direct reclaim was recorded. These are VM/cgroup-wide figures including setup and verification, not per-engine resource attribution. The host, backing device and cache were not controlled.
