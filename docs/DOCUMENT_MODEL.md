# Experimental document model

This is an embedded prototype over the same witnessed storage and transactions as the byte-key API. It is not MongoDB compatible or production-ready. It runs on `Store` or `CheckpointStore` through `DocumentDatabase`. It has no network API, access control, project isolation, distributed transactions, automatic retries, or SQL interface. Read the [storage and transaction contract](STORAGE_TRANSACTION_CONTRACT.md) before using it.

## A small example

```rust
use database_engine::{CollectionSchema, DocumentDatabase, IndexDefinition, IndexQuery, IndexValue, Store};
use serde_json::json;

fn example(store: &Store) -> std::io::Result<()> {
    let db = DocumentDatabase::new(store);
    db.create_collection("people", CollectionSchema::default())?;
    db.create_index("people", IndexDefinition {
        name: "email".into(),
        fields: vec![vec!["email".into()]],
        unique: true,
        partial: None,
    })?;
    db.transaction(|tx| {
        tx.insert("people", "ada", &json!({"email": "ada@example.test"}))?;
        tx.put_raw(b"audit:ada", b"created")?;
        Ok(())
    })?;
    let page = db.query_index("people", "email", &IndexQuery {
        equal: vec![IndexValue::String("ada@example.test".into())],
        ..IndexQuery::default()
    })?;
    assert_eq!(page.documents[0].id, "ada");
    Ok(())
}
```

The caller supplies `serde_json` to construct `Value`s. Collection names and IDs are case-sensitive UTF-8 strings; IDs are supplied separately from the object and are not MongoDB `_id` values. Names and field path components contain 1–128 UTF-8 bytes; IDs contain 1–256 bytes. Paths are vectors of object member names; dots have no special meaning and array elements are not traversed. Documents must be JSON objects. Serialized documents are limited to 1 MiB, depth 64 and 131,072 nodes. These are logical limits, not total process-memory quotas.

## Collections, writes and transactions

Create collections explicitly with a `CollectionSchema`; an empty schema accepts arbitrary object fields within limits. Each of at most 64 distinct field rules declares a path, type, required flag and nullable flag. Missing and explicit null differ; nullable does not make a field optional. An intermediate non-object makes a nested path missing. Integer rules accept signed 64-bit integers. Unlisted fields are allowed. Replacing a schema validates all existing documents atomically, subject to a 256-document/32 MiB scan limit.

Insert fails when an ID exists. Replace requires an existing ID unless `upsert` is true. Delete reports whether the document existed. `update_if` requires all explicit field conditions, where `None` means missing and `Some(Null)` means null. Ordered set, unset, checked signed 64-bit increment and array operators are applied in memory first; intermediate non-objects, integer overflow and schema or index violations fail. Set creates missing intermediate objects; unset of a missing field is a no-op; increment of a missing field starts at zero. Array push appends a value, and add-unique appends only when no existing element has the same `serde_json::Value` equality. Both create a missing array and its intermediate objects. Array remove deletes all equal elements; pop removes the first or last element. Remove and pop leave missing fields unchanged; all array operators reject a present non-array, including null. Values are validated, all changes remain within one transaction, and schema/index checks still apply. Array-valued index fields and multikey indexes are not supported. Across one update, encoded values supplied to array operators are limited to 4 MiB and array entries examined or shifted by add-unique, remove and first-pop are limited to 1,000,000; complex equality, other operations and total memory/time are not bounded by these counters. Upsert starts from an empty object. Bulk supports 1–128 ordered operations within one transaction. Collection deletion is atomic and limited to 768 keys and 32 MiB of scanned key/value bytes.

A document transaction can mix collection operations with `get_raw`, `put_raw` and `delete_raw` on unreserved byte keys. Its document, index, metadata and raw mutations use the same bounded atomic DB02 record, commit witness and synchronization as the underlying store; there is no cross-database or SQL transaction. A failed mutation aborts the entire document transaction even if its callback catches the error. Read errors do not automatically poison a transaction. Callback failure and panic discard staged changes, but external side effects are not rolled back. An I/O error during commit can have an unknown outcome and disables the underlying store until recovery. Conflicts return `WouldBlock` and callbacks are not retried automatically.

The default transaction conflicts on any intervening mutation. `transaction_with_read_set` validates point observations and complete scanned ranges, permitting unrelated writes subject to the underlying dependency limits. `transaction_until` exposes conservative, read-set and read-set-FIFO modes with operation-boundary deadlines; `DeadlineExceeded` means staged writes were not submitted, while an I/O timeout may have an unknown outcome. `transaction_controlled` additionally accepts a cloneable cancellation token and optional deadline with the same modes. An engine-reported cancellation means no staged document, index or raw-key changes were submitted; arbitrary callback or commit I/O errors are reported separately and can have unknown outcomes. Neither callbacks, lock waits nor I/O are forcibly interrupted, and callback side effects are not rolled back. Underlying snapshot, staged-record, suffix, log and other limits also apply. The ordinary store's transaction snapshot is limited to 16,384 keys and 4 MiB of key bytes; the checkpoint path has different tradeoffs documented in the storage contract.

Standalone `DocumentDatabase::get` on the ordinary store captures just the metadata and document log locations from one index state instead of copying the full index. It verifies each value and validates the metadata and document in the same order as before, then checks store health and the conservative generation under the writer barrier. Any intervening successful mutation can still return `WouldBlock`; an uncertain write still fails the read. It shares the store's active snapshot admission count, but does not reserve logical snapshot-key or key-byte budgets. It can therefore read an existing document in a store too large for a transaction snapshot. This is one read, not a multi-operation snapshot: explicit transactions retain their isolation and admission limits, and the checkpoint-backed `get` retains its existing behavior.

## Resumable schema migration

`start_schema_migration` records a pending schema, and `advance_schema_migration` validates at most 128 documents per transaction until an empty page atomically publishes it. Progress and the proposed schema persist across reopen and can be inspected with `schema_migration`; `cancel_schema_migration` removes the job without changing the active schema. A failed validation does not advance the cursor. Correct or delete the failing document and retry. One-shot `set_schema` is unavailable while a migration is pending.

From the start of a migration, every inserted or replaced document must satisfy **both** the active and pending schemas. This ensures that updates and insertions before a saved cursor cannot bypass validation. Deletions remain allowed. Incompatible old and new requirements may therefore prevent an in-place update until the migration is cancelled or conflicting documents are removed. As with index jobs, caller-scheduled steps can conflict and require retry, and existing backend transaction, memory and response limits apply. Incremental index jobs can run during a schema migration.

## Indexes and queries

Collections support up to 16 indexes, each on 1–4 distinct object paths. A partial index can require presence/absence or exact typed equality of a path. A missing indexed path omits that document; explicit null is indexed. Indexable values are null, booleans, signed 64-bit integers and UTF-8 strings of at most 256 bytes. Arrays, objects, floating-point and larger unsigned numbers are not indexable; a matching write or index build fails before commit. A compound tuple whose paths are all present is stored as one entry. A unique index enforces uniqueness across complete tuples, including null, only for documents satisfying its partial filter. String lengths and the underlying 1,024-byte key limit can reject long composite keys.

For larger collections, `start_index_build` creates a persistent build job, and `advance_index_build` scans at most 128 documents per transaction until an empty step atomically publishes the index. Writers maintain the pending index after the job starts, including inserts before the saved cursor. The index cannot be queried before publication. For unique builds, duplicate values may already exist in documents that have not yet been scanned; uniqueness is only guaranteed after completion. A duplicate or unsupported existing value stops the current step without committing its progress, so the conflicting document can be corrected or deleted and the step retried. A build can be cancelled, which starts incremental cleanup.

`start_index_drop` makes an active index unavailable immediately and removes its uniqueness constraint; `advance_index_drop` removes at most 128 index keys per transaction and persists progress through the entry and unique-key namespaces. A name remains reserved until cleanup completes. `index_jobs` lists resumable builds and drops after reopen. Each step uses a normal bounded transaction; conflicting writes can cause `WouldBlock`, and callers must retry. Steps run only when called—there is no autonomous maintenance service. The ordinary backend still requires a bounded full-index transaction snapshot; the checkpoint-backed backend has different limits. Neither provides total-memory quotas or a latency guarantee.

Document and index changes are maintained in one transaction. One-shot `create_index` scans and validates at most 256 existing documents and 32 MiB of encoded input; unique conflicts abort the build. One-shot `drop_index` is atomic and limited to 768 index keys and 32 MiB of scanned key/value bytes. These one-shot maintenance operations block or conflict according to the chosen underlying transaction mode. Incremental builds and drops are described above; schema changes can use the separate resumable validation path described above.

`query_index` explicitly chooses an index. It supports equality on a tuple prefix and inclusive/exclusive lower and upper bounds on the next field. Ordering is null, false/true, signed integer, then UTF-8 string bytes, followed by ID bytes. Partial indexes only return matching indexed documents. Pages have at most 256 documents and 16 MiB of encoded document/ID bytes. A nonempty page returns a cursor; continue until a page is empty. Pages inside one transaction share its view; independently invoked pages can observe intervening writes and are not persistent snapshots. Each page reports the selected index, supplied bound shape, entries read and rows returned. Each encountered document is checked against its 1 MiB size bound before page-byte truncation, and each returned entry and unique mapping is checked against its document. This does not detect every missing index entry caused by raw corruption. `verify_collection` compares all expected entries of declared indexes against actual entries for at most 256 documents, 8,192 index keys and 32 MiB of logical key/value bytes. It does not inspect keys for undeclared index names. `rebuild_index` can atomically remove and reconstruct a named index from valid documents when its drop, build and transaction limits are met; invalid documents or unsatisfied uniqueness prevent repair.

`query` performs a **complete bounded collection scan**, with existence/equality/typed-scalar comparisons, boolean composition, optional scalar sorting, projection, offset and limit. It fails rather than returning a silently truncated answer if its explicit scan limit (at most 1,024 documents) or 32 MiB scan budget is exceeded. The result includes actual scanned, matched, sorted and returned counts; this is a collection-scan plan, not an automatic cost-based optimizer. Sort accepts the same scalar types as indexes; missing sorts before null in ascending order, and IDs break ties in ascending order. Projection paths cannot overlap. Filtering and pagination occur before projection. The scan validates every bounded document while filtering; for unsorted queries it retains only the requested matching window. Sorted queries retain matches for sorting. Scan or stored-document errors retain precedence over an earlier filtering or sort error. These bounds are not total-memory limits.


Value predicates `In` and `NotIn` compare the whole value at an object path against a list using exact `serde_json::Value` equality, including nested objects and arrays; integer and floating-point values retain that library's distinctions. `In` requires a present path and never matches an empty list. `NotIn` negates `In`, so it matches a missing path and every document with an empty list. Explicit null is a value, distinct from a missing path. Array values are compared as whole values, with no implicit element traversal or MongoDB compatibility claim.

Array predicates `ArrayContains`, `ArrayContainsAny`, `ArrayContainsAll`, and `ArrayLength` inspect the value at an object path without traversing through arrays. They match only arrays: a missing path, explicit null, or non-array does not match. Membership uses the same exact JSON equality. `Any` with no requested values never matches, while `All` with no values matches every array; duplicate requested values do not require duplicate elements. As with other predicates, applying `Not` negates the entire result, including for missing paths. Across all value-membership and array predicates in a filter, at most 256 requested values and 4 MiB of their encoded JSON are accepted. A query fails after 1,000,000 comparisons across its evaluated documents; it never returns a truncated result. Short-circuit order affects the work performed, and nested equality can inspect substantial data, so these counters are not total CPU, memory or latency limits. The predicates also work in aggregation and transactional queries. Array predicates use a collection scan unless a different eligible equality in the same filter selects a scalar index; they do not add multikey indexing.

`query_planned` is an opt-in, rule-based alternative on both `DocumentDatabase` and `DocumentTransaction`. If exact scalar equalities are required by the whole filter (directly or under `And`) for every field of an eligible index, it can select that complete equality tuple, preferring the first qualifying unique index and then the first nonunique index. This includes compound indexes: a prefix alone does not qualify because documents missing later fields are omitted from that index. Otherwise it can select an eligible index for required scalar `Compare` predicates, combining their tightest inclusive or exclusive bounds on the field after an equality prefix. It tries eligible single-field ranges before compound ranges, preserving the earlier rule-based preference. For a compound index, every later indexed field must also be provably present through required predicates; the equality prefix may be empty. This prevents missing-field documents from being omitted. Comparisons use the same documented scalar ordering as indexes, including ordering across types. A unique equality can return at most one valid candidate; nonunique equalities and ranges are read in complete pages. Range entries arrive in value order, so the planner restores ID order before applying the full filter, sort, pagination and projection. The query fails instead of returning a truncated answer when candidates exceed `max_scanned` or their original document key/value bytes exceed 32 MiB. The limit applies to candidates examined, not just matching rows.

A required singleton `In` with an indexable value is also an equality for planning, including partial-equality proof. For a required multi-value `In` whose values are all indexable, the planner may use a single-field index as a union of exact-value probes. It deduplicates input values by index encoding, combines the existing candidate and original-document-byte limits across all probes, restores ID order, and applies the complete filter before pagination and projection. Probes share the transaction's read-set protections. Equality and range choices retain their earlier priority; a multi-value list does not use this union when any listed value is non-indexable. Union planning does not cover compound indexes or implicit array-element matching. The 256-value input limit bounds distinct probes; these are not total time or memory guarantees.

A partial index is eligible only when a required predicate proves its filter. Presence is proved by required `Exists(true)`, equality, `In`, comparison or array predicates on that path; absence requires `Exists(false)`. `NotIn` does not prove presence because it matches missing paths. Typed partial equality requires the same indexable typed equality on the same path. Explicit null counts as present. The planner does not infer individual required predicates from `Or` or `Not`, and incomplete compound tuples or non-indexable values do not qualify by themselves. If no eligible index qualifies, the method falls back to `query`'s complete scan. The result reports the selected path and actual candidate-document counts. This can succeed for a large collection when the explicit complete scan exceeds its work limit, but it is not a cost-based planner and does not handle arbitrary compound constraints or general boolean implication.

The indexed path relies on the declared index being intact. It validates each encountered index entry and its unique mapping, but an entry removed by unsupported raw writes to the reserved namespace can cause an omission. `verify_collection` can detect such omissions within its existing small-collection limits. The query holds the same transaction view, read-set range dependencies, conflict behavior, document and response limits as the underlying indexed query; it does not introduce cross-store snapshots or a total-memory guarantee.

`aggregate` performs a bounded complete scan of at most 256 documents, with count, optional grouping by one scalar path and optional checked signed-integer sum. Missing and null sum values are skipped; non-integers and overflow fail. `lookup` follows a string document ID into another collection within the same transaction snapshot. Missing/null references and missing target IDs yield no related document. It limits related document bytes to 16 MiB and rejects a projected source query. These are narrow primitives, not MongoDB aggregation pipelines or general joins.

`aggregate_stats` computes count, exact checked `i128` sum, minimum, maximum and an optional approximate floating-point mean for one to 16 distinct paths in a complete scan of at most 256 documents. Grouping uses the same typed scalar ordering and distinguishes missing from null; an empty ungrouped scan returns one zero-count group, while an empty grouped scan returns none. Each field skips missing and null independently; any present non-signed-integer value fails the operation. Matching documents are grouped as they are visited; the groups and a scan page remain in memory. Scan and filter failures take precedence over aggregation errors. The result lists the requested paths once; every group returns statistics in that same order. The exact mean is the returned sum and field count as a rational; `mean()` is approximate. The method sees transaction-staged changes and shares the scan's serializable range validation and logical limits, but is not a general aggregation pipeline, indexed aggregation, total-memory quota, or MongoDB compatibility promise.

For example, with an open `DocumentDatabase` named `db`:

```rust
use database_engine::{AggregateStatsRequest, DocumentFilter};

let report = db.aggregate_stats("orders", &AggregateStatsRequest {
    filter: DocumentFilter::All,
    group_by: Some(vec!["region".into()]),
    fields: vec![vec!["amount".into()], vec!["items".into()]],
    max_scanned: 256,
})?;
for group in &report.groups {
    for (path, stats) in report.fields.iter().zip(&group.fields) {
        println!("{:?} {:?}: count={}, sum={}, mean={:?}",
            group.key, path, stats.count, stats.sum, stats.mean());
    }
}
```

## Namespace, integrity and compatibility

The versioned byte prefix `00 65 6d 64 61 2d 64 6f 63 75 6d 65 6e 74 01` is reserved for document metadata, documents and indexes. The document transaction's raw methods reject this prefix. Direct raw `Store`/`CheckpointStore` access and older binaries do not enforce the reservation; applications must not use them to modify document-owned keys. The prefix is **not** a security or tenant-isolation boundary. Corrupt or unknown metadata and invalid documents fail when read, and queries check the entries they return; checksums and these checks do not repair corruption, authenticate data, or guarantee discovery of a missing index entry.

Collection metadata includes a version marker; unknown versions and fields fail closed. Starting an incremental index build, index drop or schema migration permanently upgrades that collection metadata to version 2. Older document readers reject it; a full-log backup and compatible engine are required for recovery. The document model uses the current experimental DB02 batch records, so older engines unable to read DB02 cannot reopen the resulting log. Earlier engines that can read the log still do not understand or protect document invariants. There is no stable format, migration or downgrade guarantee for this unreleased prototype. Backups contain plaintext document and index bytes in the full log, including prior values and deletions; they are not encrypted or authenticated. Existing independent-backup and restore requirements remain in force.
