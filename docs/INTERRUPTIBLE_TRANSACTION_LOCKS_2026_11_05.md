# Transaction lock admission: correctness and local measurements

The transaction's pre-commit writer barrier and checkpoint transaction state-lock admission now wait on a wakeable lock and check cancellation/deadlines during the wait. The writer-panic poison flag is set while exclusive access is still held, so another admitted operation observes a poisoned store rather than proceeding. A cancelled/expired result is only reported before the staged batch is submitted; successful or uncertain commit I/O keeps its prior semantics. FIFO admission releases its turn and transaction reservations on an aborted wait. Other internal locks, callback execution, automatic maintenance and I/O can still delay completion. There is no bounded latency, global fairness, physical-power-loss or total-resource guarantee.

A simple repeated `try_lock` plus sleep was rejected: in the [four-client liveness smoke](../benchmarks/results/2026-11-05-lock-polling-starvation.json), its checkpoint transactions timed out twice at five seconds while the original lock completed in 4.7–6.7 ms. This test had one continuously durable writer and no writer cap; it is an example of starvation, not a general benchmark.

A two-lock wakeable gate avoided that particular failure but incurred extra locking overhead. Its [raw results](../benchmarks/results/2026-11-05-lock-dual-gate-comparison.json) are retained rather than represented as the adopted result. The candidate instead uses one `parking_lot` read/write lock with an explicit atomic poison flag and `std`-style guard error mapping. Tests exercise writer versus reader panics, caught panics, acquisition during unwinding, timed wakeups, both stores failing closed on poisoning and reopening with their acknowledged data intact. Its performance is workload-dependent.

## Paired benchmark

The [raw single-lock results](../benchmarks/results/2026-11-05-lock-single-gate-comparison.json) contain 192 independent processes: both writable backends, plain and controlled read-only read-set transactions, one or four clients, an idle case and a case with a continuously durable writer, on tmpfs and a workspace overlay. Each client executes ten warmups and 300 measured operations. Three repetitions alternate baseline/candidate order; every completed process verifies the final writer value live and after ordinary-store recovery. The writer stops at 20,000 commits to bound storage use. Two **baseline** processes reached that cap, so they no longer represent sustained contention for their entire runs. The [driver used](../benchmarks/results/2026-11-05-lock-comparison-driver.py) records each run, source/binary hashes, CPU affinity and failures; its local paths must be adapted when repeating the experiment. The benchmark source is [`controlled_lock_bench`](../examples/controlled_lock_bench.rs).

Both binaries were built on Linux 6.18.57, glibc 2.41, Intel Xeon Platinum 8573C. The process affinity was restricted to the five CPUs available to this VM. The operating system, VM and storage were otherwise shared and caches were warm; CPU affinity does not eliminate host interference. The baseline is revision `596d2ad`, the single-lock implementation is `85562b4` (the binary was built before test-only additions in that commit), and both derive from `d22c282`. The benchmark source SHA-256 was `a1a7fc5839c58f7cfce07c6e4487745af9f8d10ae649a6fcbedecf6443517b10`; baseline and candidate binary hashes are recorded in the raw file. These are short synthetic read-only transactions, not SQL/MongoDB comparisons or throughput capacity claims.

For each process, p50 and p95 were calculated from the measured latencies; the table reports the median across the three processes for each percentile, in microseconds. The p95 is calculated from the sorted samples at index `floor(0.95 * (n - 1))`.

| Filesystem | Backend | Workload / clients | Baseline p50 / p95 (µs) | Single lock p50 / p95 (µs) |
| --- | --- | --- | ---: | ---: |
| tmpfs | checkpoint | idle / 1 | 0.167 / 0.168 | 0.174 / 0.176 |
| tmpfs | checkpoint | idle / 4 | 0.304 / 1.522 | 0.670 / 2.267 |
| workspace | checkpoint | idle / 4 | 0.280 / 2.824 | 1.304 / 3.636 |
| tmpfs | checkpoint | writer / 4 | 0.212 / 18.883 | 0.234 / 16.531 |
| workspace | checkpoint | writer / 4 | 0.210 / 2.123 | 0.312 / 2.664 |
| tmpfs | ordinary | writer / 4 | 0.410 / 81.088 | 0.680 / 33.350 |
| workspace | ordinary | writer / 4 | 0.398 / 2.324 | 0.550 / 350.933 |

In the workspace ordinary/controlled/four-client writer runs, baseline process times were 1.40–4.52 seconds and individual maximum transaction samples 281–527 ms, with 4,884–15,583 writer commits. The candidate finished in 32–43 ms, with maximum samples 1.9–3.2 ms and 58–112 writer commits. The candidate's worse p95 in that case coexists with a much lower maximum and shorter process lifetime: the schedulers distribute time between transactions and the writer differently. Writer counts are **not** an equivalent throughput comparison when durations differ. The checkpoint workspace case showed a similar shorter lifetime but one run is not evidence of an absolute starvation bound. Idle four-client checkpoint medians regressed materially. Do not infer that either lock is always faster or that cancellation completes within the periodic check interval.

The stable debug and optimized all-target matrices, Rust 1.85 debug all-target matrix and both clippy checks passed. A [350-run stress campaign](../benchmarks/results/2026-11-05-lock-stress.json) repeated FIFO release, cancellation, poison and reopen checks 25 times per test on each filesystem. Four [additional 60-second model fuzz runs](../benchmarks/results/2026-11-05-interruptible-lock-fuzz.json) exercised 50,381 generated inputs across controlled transactions, ordinary and checkpoint read-set transactions, and the checkpoint store without a finding. Fuzzing does not exhaust thread schedules; process termination is not a power-loss test. Physical power-loss and independent off-host restore remain deferred as recorded in the foundation checklist.
