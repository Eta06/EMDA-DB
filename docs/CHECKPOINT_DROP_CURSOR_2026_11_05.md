# Checkpoint-backed collection deletion cursor

The checkpoint-backed store now persists a cursor after a full deletion page, atomically with the deleted keys. The first cursor step changes the collection marker from version 3 to version 4. A later ordinary-store open can resume the job, and the final step scans every document and index namespace from its beginning before atomically removing the cursor and metadata. A missing, malformed or inconsistent cursor fails closed; a valid-looking cursor that skips surviving keys causes the final check to fail. A byte-limited short page is never treated as completion. Existing version 3 jobs without a cursor still resume. Older document readers reject version 4; see [versioning](VERSIONING.md#experimental-document-format).

## Paired deletion measurements

We compared release builds of the same [workload](../examples/collection_drop_bench.rs) on baseline `c4064d4` and candidate `8490fd0`. Each run used one client, a unique index, up to 128 keys per synchronized deletion step, and checked the exact removed-key count and content after recreation and full-log reopen. Each number is the median of four per-run sums of step latencies, in milliseconds. Marker creation, preparation, recreation and reopen are outside step timers. Both variants used V3 on the tested filesystems.

For the sampled 3,000-document checkpoint case, the median total fell by about 35–37% on the workspace overlay and 59–64% on tmpfs. Small cases and ordinary-store results varied, including the slower measurements shown above. The cursor adds 1,973 bytes at 1,000 documents and 5,509 bytes at 3,000 documents in this workload; this counts the main log only, not total disk usage, and can make existing caps reject sooner. A short page does not create a cursor until a later full page, so the 100-document case adds no cursor records here.

Individual slow steps still occur. With 3,000 checkpoint documents, each run had fewer than 100 steps, so its p99 is effectively its maximum. Overlay candidate maxima ranged from 1.733 to 11.733 ms in the primary run and 1.255 to 6.262 ms in the repeat; the corresponding baseline ranges were 1.410–3.923 ms and 1.392–2.914 ms. These small samples do not establish a tail-latency bound.

The [overlay](../benchmarks/results/2026-11-05-drop-cursor-threshold-overlay.json.gz), [overlay repeat](../benchmarks/results/2026-11-05-drop-cursor-threshold-overlay-repeat.json.gz), [tmpfs](../benchmarks/results/2026-11-05-drop-cursor-threshold-tmpfs.json.gz) and [tmpfs repeat](../benchmarks/results/2026-11-05-drop-cursor-threshold-tmpfs-repeat.json.gz) retain every step sample, log length, binary and script hash, errors and telemetry. Of 192 quiet checks, 191 passed. Across the full process windows, VM steal reached 20% and I/O wait 17.89%; no cgroup CPU throttling or direct reclaim was recorded. These VM/cgroup figures include preparation and verification, are not per-engine resource attribution, and the overlay backing device was not independently verified. The tests do not measure concurrent load, total memory, physical power loss, off-host restore or another database engine.

## Ordinary document regression checks

The same candidate and baseline were also compared with SQLite using the existing single-client document CRUD workload at 100 and 1,000 preloaded indexed documents. The [overlay](../benchmarks/results/2026-11-05-drop-cursor-threshold-document-overlay.json.gz), [overlay repeat](../benchmarks/results/2026-11-05-drop-cursor-threshold-document-overlay-repeat.json.gz), [tmpfs](../benchmarks/results/2026-11-05-drop-cursor-threshold-document-tmpfs.json.gz) and [tmpfs repeat](../benchmarks/results/2026-11-05-drop-cursor-threshold-document-tmpfs-repeat.json.gz) contain all operation samples. For 1,000 documents, median-of-run-median ordinary reads changed from 6.52 to 6.05 µs on overlay, 6.77 to 7.23 µs in the repeat, 2.74 to 2.59 µs on tmpfs and 2.85 to 2.52 µs in its repeat. Other operations and tails vary in the raw files; these short tests do not establish a general speedup or eliminate regressions. SQLite uses a different JSON representation and validation path.

An earlier checkpoint-only prototype placed an optional cursor field in all collection metadata. Its [compressed source patch](../benchmarks/experiments/2026-11-05-metadata-drop-cursor.patch.gz), deletion results ([overlay](../benchmarks/results/2026-11-05-drop-cursor-selective-overlay.json.gz), [repeat](../benchmarks/results/2026-11-05-drop-cursor-selective-overlay-repeat.json.gz), [tmpfs](../benchmarks/results/2026-11-05-drop-cursor-selective-tmpfs.json.gz), [repeat](../benchmarks/results/2026-11-05-drop-cursor-selective-tmpfs-repeat.json.gz)) and ordinary CRUD results ([overlay](../benchmarks/results/2026-11-05-drop-cursor-document-overlay.json.gz), [repeat](../benchmarks/results/2026-11-05-drop-cursor-document-overlay-repeat.json.gz), [tmpfs](../benchmarks/results/2026-11-05-drop-cursor-document-tmpfs.json.gz), [repeat](../benchmarks/results/2026-11-05-drop-cursor-document-tmpfs-repeat.json.gz)) are retained. The patch applies to `c4064d4` after decompression. The final format instead uses an explicit version and separate cursor key, avoiding a new serialized field on normal collection metadata. The earlier measurements were variable and do not prove the field alone caused any latency change.

## Correctness and compatibility checks

Stable, optimized stable and Rust 1.85 full local suites passed 846 tests at `8490fd0`; stable and Rust 1.85 all-target Clippy and 50 Python tests passed. Tests cover a 32 MiB byte-limited short page, old version 3 markers, backend switching, blocking and online compaction, backup/restore, concurrent workers, forged and inconsistent cursors, and stray-cursor rejection. Checkpoint V2 and V3 tests injected all 330 append cut points for an initial cursor step and all 162 for a later cursor update, plus selected panic, synchronization and V3 metadata-witness failures. These check atomic recovery or fail-closed preservation on a running OS, not physical power failure.

The [stress campaign](../benchmarks/results/2026-11-05-drop-cursor-stress.json) repeated seven fault, concurrency and online-handoff tests ten times each on tmpfs and on the workspace overlay: 140 successful invocations. The byte-limited short-page test also passed separately on the overlay. Other validation was active during the stress run and the overlay backing device was not independently verified.

Four address-sanitized [model campaigns](../benchmarks/results/2026-11-05-drop-cursor-fuzz.json) ran 39,158 generated deletion, index, document and checkpoint histories without a finding. A [compatibility probe](../benchmarks/results/2026-11-05-drop-cursor-format-compatibility.json) built the same [probe source](../examples/drop_format_compat_probe.rs) against both revisions: the old reader rejected an active version 4 marker and the new reader completed and recreated the collection. These finite local checks do not establish exhaustive concurrency, recovery or deployment guarantees. Physical power-loss and independent off-host restore remain separately deferred.

Follow-up fault tests at `e0b5fe0` also compare the recovered cursor bytes and metadata version with the receipt for both the first and later cursor steps. They cover all 140 append cut points for final cursor and metadata removal on each of V2 and V3, plus selected panic, sync and V3 witness failures. A [separate stress run](../benchmarks/results/2026-11-05-cursor-atomicity-stress.json) repeated five fault tests ten times on each local filesystem: 100 successful invocations. These checks exercise finite simulated I/O failures; they do not establish physical power-loss behavior.
