# Storage and transaction contract

This document separates **current prototype behavior** from **design targets that are not implemented**. It is not a production durability, isolation, or recovery guarantee. The same core contract must eventually govern key-value, document, and SQL interfaces when they operate on the same database. Each new interface must state its scope and any restrictions before it is shipped.

## Non-negotiable optimization rule

No performance optimization is accepted if it violates the durability, isolation, or recovery guarantees in force for the feature. This rule also protects the prototype's documented behavior; the absence of a production guarantee is not permission to weaken its write synchronization, coordination, corruption detection, or recovery behavior. This applies to zero-copy access, caching, memory mapping, async I/O, compression, group commit, SIMD, assembly, and adaptive storage alike. The faster path must preserve the same contract, fail safely, and pass the same correctness and fault tests. Benchmarks compare equivalent guarantees; disabling synchronization or weakening isolation to obtain a better number does not meet this rule.

## Current prototype: one store in one process

### Successful writes and ordering

- Each `put` or `delete` appends one checksummed record and returns success only after the log data and in-memory index update complete. V2 stores update and synchronize an independent commit-witness file after synchronizing the log. V3 stores append records, update a checksummed boundary in the log inode's `user.db.commit.v3` extended attribute, then perform one full `fsync` covering both file data and metadata before publishing the index or acknowledging the write. `fdatasync` is insufficient for this V3 metadata guarantee. A separate immutable identity anchor is synchronized at creation and checked during writes and backups. Legacy stores synchronize the log only and retain the limitations below. One log leader appends records in queue order. Concurrent single-key mutations can share a synchronization; grouping does not make them an atomic multi-key transaction. Deleting a missing key writes a deletion record. Deleted and superseded values remain in the append-only log and full-log backups; delete does not perform secure erasure.
- Readers share an index read lock to select a value's location and can observe the previous indexed value while a writer synchronizes; the index update is exclusive. Once selected, the immutable log location is read and verified without holding the index lock. A read beginning after a successful write returns that value unless a later mutation replaces or deletes it, or an I/O/corruption error occurs. An overlapping read can select either the old or the new location, including completing after a later write.
- Single-key mutations concern one key. `write_batch` encodes up to 1,024 ordered puts/deletes and 16 MiB of encoded payload in one checksummed `DB02` log record, synchronizes it before acknowledgement, and publishes every index update under one lock. A `get_many` or snapshot sees either the index before or after the batch. Incomplete or corrupt batches fail closed; a complete unacknowledged batch can be adopted in its entirety on recovery. Batch errors after append have an unknown outcome and poison the store. Batches require V2/V3 witnesses and block other writers during commit; older readers cannot parse `DB02`. When a live-key limit is configured, each ordered intermediate batch state must stay within it, both at admission and during replay. A batch is a blind atomic write, not a read-modify-write transaction. `compare_exchange` serializes a single-key comparison and mutation against other writers; a mismatch does not write, and a matching mutation uses the ordinary sync-before-acknowledgement path. It compares values rather than versions and does not detect ABA changes. `increment_i64` likewise serializes against writers; it treats a missing key as zero and stores a checked, eight-byte little-endian signed integer. Invalid encoding and overflow do not write. Both conditional operations currently exclude all concurrent writers, even on other keys. `scan` captures ordered key/immutable-value locations under the index lock and reads those values after releasing it; each page is limited to 1,024 entries and 32 MiB of key/value bytes. Different pages can observe concurrent updates and are not a transaction snapshot. `get_many` captures its selected locations under one index lock, preserving request order and duplicates; it rejects requests of more than 1,024 keys or 32 MiB of key/value bytes and returns no partial result on error. Deleted values already selected by an overlapping scan or bulk read can still be returned. There is no user-visible sequence number or change stream. Reads return owned bytes; the engine does not offer zero-copy reads.
- An OS advisory lock prevents cooperating processes from opening the same store at once. This is not a security boundary or a guarantee against processes that ignore the lock.
- The commit coordinator reserves capacity before preparing records and limits reserved and queued encoded sizes awaiting completion to 64 MiB and 1,024 records, with up to 64 records per sync. Preparation happens outside the queue lock; overlapping writes can enter the queue in a different order from their reservations. Writers wait when admission is full. This bounds encoded bytes, not total process memory or the number of caller threads; there is no timeout or service-level admission policy. Backups wait for in-flight writes and exclude new writes while the log is copied.
- `open_with_log_limit` applies an optional per-open maximum log-file length. Before entering group commit, each mutation reserves the complete encoded record length against a counter that includes the initial log and all committed or in-flight reservations. A request is rejected before append if the cap cannot accommodate it; pending reservations may temporarily cause rejection even if an earlier request later fails before append. Pre-append errors release their reservations. I/O errors after a permitted append have an unknown outcome and poison the instance; reopening checks the actual log length before replay and reconstructs the counter. Independent writes may share a sync. The cap counts headers, replaced values and tombstones; even a delete can be rejected. It is not persisted, and opening can initialize a new store before the length is checked. Other files, memory, external modification and total project storage are outside this limit. Normal `open` has no cap.
- `open_with_limits` can also limit the number of live keys for that open instance. New keys are rejected once the cap is reached; updating existing keys and deleting keys remains allowed if any log-length limit also permits the record. Membership-changing operations serialize for admission so concurrent operations cannot oversubscribe the key count. Updates to already-present keys hold a shared membership barrier through acknowledgement and may share a sync; inserts, deletes and compound mutations wait for that barrier. Recovery checks the count before inserting each new key and fails closed if any historical log prefix exceeds the limit, even if later deletes would reduce the final count. Such a failure does not modify the log or advance the commit witness. The setting is not persistent, and the count does not establish a byte or process-memory bound. Ordinary `open` has no limits.
- `open_with_resource_limits` additionally accepts a per-open limit for the combined lengths of currently live keys. A new key is rejected before append if it would exceed the limit; updates do not add key bytes and successful deletes free them. Under the exclusive membership barrier, the live-byte counter advances only after a successful membership-changing commit; already-present key updates may share synchronization and cannot change the counter. A failed commit keeps the store unusable until reopening reconstructs the counter. Ordered batches check every intermediate operation, and transactions check their encoded delete-before-put order. Full recovery enforces the cap across all historical prefixes and every ordered batch operation before adopting an unacknowledged tail. A historical peak can prevent opening even if the final live set fits; separate-copy compaction may reduce it. The cap must be supplied again on every open and is unavailable through checkpoint recovery, whose current format does not record the historical live-byte peak. It excludes index allocation overhead, values, snapshots, log and other files, other stores and total process memory; it is not a persistent project quota or security boundary.

### Crash, power failure, and uncertain outcomes

- After a successful return, the prototype has requested synchronization of the appended log data and, for a new-format store, the commit witness. The intended process-crash behavior depends on the filesystem and device honoring synchronization, including persistence of xattrs by a full inode `fsync` for V3. Before that sync completes, V3 data and boundary metadata can reach storage in either order; a boundary ahead of valid data fails closed. A DB02 batch is one atomic record; grouping independently submitted records does not make them one transaction. V2 retains its original ordered two-file synchronization. The tests cover reopening after a killed process and injected I/O faults, not every crash point or hardware failure.
- If append or synchronization returns an error, some or all bytes may already have been written. Unacknowledged mutations in the affected group and queue fail with **unknown** outcomes, and this store instance refuses further reads and writes until reopened. A complete but unacknowledged record can appear after recovery. A panic in the commit leader also fails the store and wakes waiting writers. Completed requests are signaled individually, and queued requests periodically recheck leadership; scheduling and wait times remain unbounded. There is no request-id or retry-deduplication guarantee.
- On reopen, the engine scans the log in append order using a bounded read buffer, verifies every record, and refuses to open an incomplete final record, invalid header, or checksum error without truncating the log. New-format stores have a checksummed witness tied to their log identity. If the intact witness records an offset missing from the log, including truncation exactly at a record boundary, opening fails. A missing, incomplete, corrupt, wrong-identity, or non-boundary witness also fails closed. A complete valid tail beyond the witness may be an unacknowledged write: recovery synchronizes that log and advances the witness before returning. An incomplete tail is never silently truncated. A failed witness update has an unknown outcome and the open instance refuses further operations.
- The log and witness share a filesystem and are not independent backups or replicas. V3 keeps its boundary outside the log byte stream, so truncation or rollback of just log bytes is still detected when it removes the witnessed boundary; missing metadata also fails closed. Rollback of the data and witness together (including a V3 inode or filesystem snapshot), rollback of the witness alone to an older valid value, equal-length replacement with valid earlier records, checksum collisions, or storage that violates synchronization assumptions can escape detection. Neither format authenticates record history or protects against an adversarial filesystem. Corrupt witnesses fail closed; they do not reconstruct damaged data. Legacy `DB01` logs have no witness, so loss at a complete record boundary can still go undetected. `Store::upgrade_format` creates a verified non-overwriting copy in the current format; `Store::upgrade_legacy` remains a legacy-only wrapper. Conversion establishes a witness at the data currently present; it cannot discover loss that occurred before the upgrade. Independent verified backups remain necessary.
- Store initialization synchronizes the path and its ancestor directories, but no universal power-loss guarantee is established: underlying filesystem and device behavior matters, and actual power-cut testing is absent. Full-log backup/restore is experimental and depends on supported filesystem operations; independent backups and restore drills are still necessary. Do not use this prototype for important production data.
- An existing zero-byte log is rejected because it may be an interrupted initialization, an empty legacy store, or lost data; ordinary open never silently chooses the unwitnessed legacy format. After independent verification, `Store::upgrade_empty_legacy` takes the source lock, requires an empty regular log with no external or metadata witness, and publishes a new witnessed store at a nonexisting destination. It cannot establish whether the source lost data and may create a source lock file. A validated backup with a zero-byte legacy log restores as a new witnessed empty store with a new identity; this is an intentional format change for that case. Neither path authenticates the source or reconstructs missing data. A dangling external witness symlink is treated as an existing invalid entry and cannot authorize creation or legacy fallback; directory access still requires trusted, cooperating actors.

### Isolation, snapshots, and interfaces

- `Store::transaction` provides an experimental optimistic serializable transaction within one open store for point and ordered range reads and staged puts/deletes. It captures an index snapshot and an in-process generation under the same read lock. Transactional reads see that snapshot plus staged writes. Before commit it takes the exclusive writer barrier and rejects with `WouldBlock` if any mutation has published since the snapshot, including a write to an unrelated key or an ABA change. Thus a successful transaction can be serialized at its validation/commit point relative to other transactions and ordinary store mutations, subject to the stated storage assumptions. Conflicts never append the staged writes; there is no automatic retry. A callback error or panic discards staged writes; external side effects are not rolled back. A successful write transaction commits one DB02 record, synchronizes before returning, and requires a witnessed V2/V3 store. Commit I/O errors have an unknown outcome and poison the store. Read-only transactions do not append. Transactions use the read-snapshot limits and aggregate snapshot budget, so stores over 16,384 keys or 4 MiB of key bytes cannot currently start one; staged writes are limited to 1,024 keys and 16 MiB of encoded operations. The generation is process-local and resets on reopen; snapshots and transactions cannot outlive the store. There are no distributed or cross-project transactions, bounded-completion or fairness guarantees, automatic retry or external side-effect rollback, or compatibility claims for SQL/document interfaces. This is a prototype and not a production isolation guarantee.
- `CheckpointStore::transaction` captures a process-local generation without copying the index. Each point or range read holds the state read lock while checking that generation and reading the verified checkpoint plus suffix, then merges staged changes. Final validation and any atomic DB02 commit hold the state write lock. Every successful mutation advances the generation; generation exhaustion rejects a write before append, while checkpoint rollover alone does not change it. Thus an intervening mutation, including unrelated writes and ABA changes, makes subsequent reads and final validation fail with `WouldBlock`. Even a callback that catches a conflict cannot commit its staged changes. Successful transactions serialize at final validation/commit; read-only transactions append nothing. Callback errors and panics discard staged changes, but external effects are not rolled back and callbacks are not automatically retried. Writes are synchronized and have the same unknown-outcome rules as other checkpoint-store writes. Staging uses the 1,024-key and 16 MiB batch limits and a 64 MiB encoded-record budget across concurrent transactions on this open store; response copies, allocations, checkpoint buffers and commit encoding are excluded. This path has no global fairness or total-memory guarantee; the shared active-transaction admission limit below applies.
- `CheckpointStore::transaction_with_read_set` records immutable point locations and complete requested scan ranges without copying the full index. When the generation changes, it revalidates prior observations under the state read lock before returning another read or accepting a staged write; it also validates under the state write lock before commit. This prevents callbacks from observing a fractured pair across an atomic update. A successful callback's observations match its commit state, even when unrelated writes occurred between reads. A changed observation returns a sticky conflict; changing and restoring a present value has a different location, while an insertion and deletion never observed by the transaction can leave the same absence or range. Each scan records all entries in its requested bounds, including entries beyond a limited page, so phantoms and changes anywhere in that range conflict. Dependencies are capped at 2,048 distinct points and ranges, 2 MiB of retained keys and bounds, and 65,536 total point/range items per transaction. Retained key bytes and fixed point/range metadata reserve from the same 64 MiB per-store budget as staged records; allocator/map overhead, vector capacity slack, response copies and validation buffers are excluded. During capture, reservations grow in quanta, potentially reserving extra space temporarily; unused space is released before returning a page. Near the limit, exact reservations are attempted. Duplicate ranges share an observation. Capture or admission failure returns before an untracked page or point value is returned. Capturing and revalidating large ranges can be expensive and hold a state lock while reading checkpoint blocks; the per-validation item cap does not bound total callback work. Independent store reads and external effects are outside the transaction. `transaction_with_read_set_fifo` uses the same validator with FIFO callback and commit admission.
- `CheckpointStore::transaction_with_fifo` uses the same conservative validation but joins a FIFO queue before beginning its callback. The queue accepts at most 16 participating transactions and releases a turn after the state write guard and staged reservations, including on errors and panics. Other transactions and independent writes remain outside the queue and can still cause conflicts. A callback must not wait for another FIFO transaction on the same store; same-thread nested admission returns an error, but cross-thread dependency cycles cannot be detected. Slow or stalled callbacks delay later participants. The queue is not a bounded-response or global fairness guarantee.
- `CheckpointStore::transaction_until` accepts a monotonic deadline and conservative or read-set validation, with or without FIFO admission. It checks expiry before admission, after queue and state-lock waits, after the callback, and immediately before commit, including after automatic checkpoint maintenance and before append. FIFO admission removes expired waiters. `TimedTransactionError::DeadlineExceeded` means this transaction's staged changes were not submitted; `Operation` wraps callback and I/O errors, including an I/O timeout during commit whose outcome may be unknown. Transaction reads and staging started after expiry return `TimedOut`; a callback that forwards that error returns `Operation`. Callbacks, state-lock waits and I/O are not forcibly interrupted, and a commit already started can succeed after expiry. External callback side effects are not rolled back. Deadlines do not provide bounded completion.
- `CheckpointStore::snapshot` captures the current verified checkpoint block directory and bounded suffix overlay under the state read lock, sharing the read-only log handle and duplicating the checkpoint file descriptor. It does not copy the full base index or values. Its point, bounded bulk and ordered paginated reads use captured immutable log locations, including overlay tombstones, despite later mutations and checkpoint rollover. Reads hold the store's state read lock and fail if a prior write left the instance unusable; checkpoint blocks and values retain their existing checksums. One open store permits at most 16 active views, 262,144 copied block-directory entries, 65,536 copied overlay keys and 16 MiB of copied overlay-key bytes across them. Per-view block, overlay-key and key-byte limits can be lowered. Counts exclude allocator capacity, returned data, file buffers and total process memory. Creation errors and panics release reservations; `cancel` or drop releases the captured view before its reservation. A monotonic deadline rejects operations begun after expiry, but does not interrupt lock waits or I/O. A later snapshot request or explicit `reap_expired_snapshots` call reclaims expired idle views; in-progress reads are skipped. An explicitly started snapshot reaper can schedule checks; without it, an expired view can retain resources until reaping, cancellation or drop. Snapshots borrow the store, do not survive reopening, and rely on the source log remaining append-only. They do not provide write transactions or safe live-log reclamation.
- `transaction_with_read_set` is an opt-in serializable mode using the same snapshot, writer barrier and atomic commit. When the generation changed, it compares each point read against the current index and compares every entire requested scan range, including entries beyond the returned page. Matching key membership and immutable log locations mean the transaction's snapshot observations still match the state at validation; its staged writes can then be serialized at that point. This reasoning depends on locations remaining immutable and not being reused while transactions exist; any future live compaction must preserve that property or introduce a validated version identity. Reads of a transaction's own staged entry need no base dependency. A present value changed and restored has a different location and conflicts. A previously absent key inserted and deleted before validation can return to the same absent state without a conflict; this is not an absence-version or change-notification guarantee. Changes outside the read dependencies may commit without conflict. Read dependencies are limited to 2,048 distinct point/range constraints and 2 MiB of key/bound bytes per transaction; failure is reported before returning an untracked read. Validation examines at most 65,536 point checks or pairs of range entries; exceeding that work limit returns an error without committing. Allocator overhead is excluded. Full-range validation holds the writer barrier and can be expensive. Reads through independent `Store` methods, callback side effects and other processes are not included. The existing conservative `transaction` semantics remain unchanged.
- `transaction_with_read_set_fifo` uses the same validation and commit rules with an optional FIFO admission queue after callbacks finish. A turn is released after the writer barrier is released, including on unwinding. The queue is limited to 16 entries and fails closed if poisoned. It orders only calls to this method; regular writes, other transaction modes, scheduling delays and I/O are outside that order. It does not promise a wait-time bound and may increase latency or conflict retries. Existing transaction methods do not use this queue.
- `transaction_until` accepts a monotonic deadline and a choice of conservative, read-set or read-set FIFO validation. It checks expiry before callback admission, after the callback, after acquiring the writer barrier and immediately before beginning commit; FIFO admission also removes expired waiters. The distinct `TimedTransactionError::DeadlineExceeded` is returned only before that transaction's staged batch is submitted. `TimedTransactionError::Operation` wraps callback, validation, admission and I/O errors; an I/O error of kind `TimedOut` during commit can have an unknown outcome and must not be treated as an engine-confirmed abort. A callback forwarding an expired snapshot read yields `Operation`. Callbacks, writer-lock waits and I/O are not interrupted; if expiry occurs after the final check, a commit can complete and succeed after the deadline. External callback side effects are not rolled back. Deadlines are not cancellation tokens or bounded-response guarantees.
- `transaction_controlled` on `Store`, `CheckpointStore` and `DocumentDatabase` adds a cloneable, one-way cancellation token and an optional deadline. The engine checks cancellation before and after callbacks, at transaction-operation boundaries, while waiting for FIFO admission, after acquiring the writer/state lock and immediately before submitting a batch; checkpoint commits recheck after automatic rollover. Queued controlled waiters poll cancellation at 10 ms intervals, but scheduling and lock delays are not bounded. `ControlledTransactionError::Cancelled` or `DeadlineExceeded` means that transaction did not submit its staged changes. A private marker distinguishes cancellation from arbitrary callback or commit `Interrupted` errors; those remain `Operation` errors and commit failures can have unknown outcomes. Once commit begins it can succeed after cancellation, and callbacks, external effects, ordinary lock waits and I/O are not forcibly interrupted. Successful rollover maintenance may precede a cancelled checkpoint transaction.
- Concurrent transactions on one open store share a 64 MiB budget for encoded staged records, including each staged key, value, record header and checksum but excluding the per-batch count field. A reservation is acquired before a staged entry grows; if admission fails, that entry and all earlier staged changes remain unchanged. A callback can catch the error and continue, or propagate it to abort. Replacements that shrink release their excess reservation; transaction completion, callback error and unwinding release the remainder. The budget does not include allocator overhead, snapshots, returned values, commit encoding buffers, independent batches or other stores; it is not a total memory limit or fair scheduling guarantee.
- A standalone `DocumentDatabase::get` on the ordinary store is a two-point conservative read. It reserves one of the same 16 active snapshot/admission slots, captures collection-metadata and document locations plus the generation under the index lock, and reads and verifies those immutable log values in order. Before returning a successful result it takes the writer barrier, checks for an uncertain write, and rejects any intervening mutation with `WouldBlock`, just as the prior read-only conservative transaction did. Error paths release admission and do not return partial data. It does not retain an index root or reserve logical snapshot-key budgets, so it can read a large ordinary store even when a full transaction snapshot would exceed its limits. The callback is engine-internal and has no user side effects. Explicit document transactions and the checkpoint-backed `get` are unchanged; separate standalone reads do not share a snapshot.
- `Store::snapshot` retains an immutable shared index root and generation under the read lock and borrows the store until dropped; snapshot reads and paginated scans use those immutable log locations despite subsequent writes. It rejects requests over caller-supplied limits and hard per-snapshot caps of 16,384 keys and 4 MiB of key bytes. Per open store it also limits active snapshots to 16, aggregate logical snapshot keys to 65,536 and aggregate logical snapshot key bytes to 16 MiB, counted per view even if roots are shared. Reservations are released on drop and on unwinding during construction. A write against a shared root may copy the full index; the coordinator prepares a copy outside the exclusive index lock when possible and checks the root identity and generation before publication. A snapshot racing after that preparation check can still cause a copy under the lock. Publication and acknowledgement remain after log synchronization. Map overhead, returned values, multiple stores and total process memory are not covered by those counters. A poisoned store rejects new snapshot reads. Snapshots are process-local, cannot outlive the store, and do not provide write transactions or survive reopening. Old log locations remain available because the live log is append-only; there is no automatic version garbage collection or automatic live-store compaction. Without explicit compaction the log grows, and its key index is held in memory. `compact_to` verifies the complete source log and its live index, writes only live records into a separate staging store, reopens and verifies it, and publishes it without replacing an existing path. It blocks mutations during copying but leaves the source and its readers intact; changes after it returns are absent from the copy. A failure syncing the destination parent after publication has an uncertain outcome. It does not bound memory, provide automatic switchover, or make historical data in the source or older backups disappear.
- A caller can explicitly cancel a read-only snapshot, which releases its retained index view before releasing its reservation; cancellation is idempotent and subsequent reads return an error. `snapshot_until` provides an optional monotonic deadline: creation and new read/scan operations at or after expiry return `TimedOut`. An operation started before expiry can finish later; neither lock waits nor I/O are interrupted. A later snapshot request or explicit `reap_expired_snapshots` reclaims expired views without waiting for an in-progress read; busy views are skipped for a later attempt. The deadline registry is bounded to 16 entries; a new deadline snapshot can fail temporarily if stale entries are busy. An explicitly started snapshot reaper can schedule checks; without it, an idle expired view can retain its reservation until reaping, cancellation or drop. Cancellation does not affect other snapshots or transactions, and a cancelled snapshot still borrows the store until dropped. Standalone `Store` snapshots do not enable live-log reclamation; `OnlineStore` provides a separately guarded handoff and explicit reclamation described below.
- `Store::start_snapshot_reaper` and `CheckpointStore::start_snapshot_reaper` optionally run one worker per open store, periodically or on coalesced request. They use the existing idle-only reaping operation, never interrupt in-progress reads, and leave snapshots without deadlines alone. Check counts, reclaimed views, shutdown and failures are exposed in status; errors and panics stop the worker. Stop and drop join it and can wait indefinitely for a lock or in-flight check. The worker holds an `Arc` to its store, is not persistent or automatically started, and provides neither a total-memory quota nor a reclamation-time guarantee.
- Ordinary `Store::compact_to` writes ordinary `DB01` records to a private staging store in groups of at most 64 records and 4 MiB encoded bytes, except that a single larger record forms its own group. Each group is synchronized with the target's applicable witness protocol. The target index is rebuilt by reopening, and the copy is checked against the source before non-overwriting publication. A copy or synchronization failure does not publish the staging directory; a parent-directory sync failure after publication has an uncertain outcome. This is not atomic switchover or live compaction, and the group size is not a total-memory quota.
- The Linux-only `OnlineStore` guards an ordinary `Store` behind callback-scoped access. It captures a bounded index snapshot and a synchronized log boundary, verifies the complete historical prefix against that snapshot, copies live keys to a private target and replays later witnessed source records in order while callbacks continue. Each catch-up boundary excludes in-flight writes. It then waits for all callbacks, replays a limited final suffix, verifies the target log and compares every live key and value, reopens it with the original per-open limits, publishes an unused sibling, and exchanges the two directories while holding both locks. The parent directory is synchronized around publication and after exchange. A failure before exchange leaves the source active and may leave the compacted sibling; after exchange or its directory-sync failure the handle is disabled and both paths must be reopened and inspected. Both paths contain the same acknowledged live state at the handoff under the documented synchronization assumptions; the old directory is retained and can contain deleted historical data. Callers must coordinate through this handle, not hold snapshots or transactions outside callbacks, avoid same-handle reentry and cross-thread dependency cycles, and use a trusted same-parent directory with current cooperating clients. Unknown source files and managed checkpoint metadata are rejected. The operation may write `DB02` records unreadable by older readers, and old external checkpoints must be recreated. Limits cover logical snapshot keys/key bytes, historical peak, bounded catch-up rounds, final suffix and target log, not total memory or disk. Full-prefix and target verification and the final callback pause have no time bound; checkpoint-store online handoff and physical power-loss validation remain open; optional scheduling is described below. Process-kill and injected-error tests exercise selected publication boundaries on the running OS only.
- `OnlineStore::compact_and_reclaim` optionally removes that old copy only after the new store was verified, exchanged and the parent ancestry synchronized. Callback-scoped snapshots and transactions have finished before handoff; the retired store's exclusive lock and the replacement's write barrier are held during cleanup. Direct reads that do not require the write barrier can use the new store; mutations and barrier-dependent reads wait until cleanup finishes. The old directory is renamed without replacement into an engine-owned private staging directory before its lock file is removed. Known files are unlinked, the retired and staging directories are synchronized and removed, and the parent ancestry is synchronized. This avoids deleting a different store created at the previous path after the move. A cleanup error is distinguished from a handoff error and leaves the live handle usable; the old copy may be partial or retained under a marked staging path, and marker retention can itself fail. A process kill or panic can leave cleanup for explicit inspection and the scoped retired-stage method below; a panic can poison a state or maintenance lock and require reopening. This depends on trusted same-parent directories, cooperating clients, and filesystem synchronization assumptions; it is not secure erasure, a total disk quota, scheduled garbage collection, or a physical power-loss guarantee.
- `OnlineStore::start_reclamation_worker` opts into periodic or explicitly requested checks of the same reclaim operation. It permits one worker per handle, checks a synchronized log boundary and configured minimum length, and after its own successful handoff waits for configured growth from the boundary observed afterward on the same store identity. A manually replaced store resets that baseline; another operation can also change the store between observation and compaction. The thresholds are scheduling hints, not hard limits. If the maintenance lock is held before compaction begins, the worker records a `busy_checks` deferral and retries only on a later scheduled or requested check. This case is identified separately from a generic `WouldBlock` I/O error; other failures stop the worker and retain the underlying operation’s uncertain-outcome rules. It reports known successful handoffs and cleanup status separately. Panic is reported as requiring inspection and reopening. It holds a store reference and waits for an in-flight check when stopped or dropped; callbacks must not wait for the worker. The worker is not persistent, does not automatically retry uncertain failures or clean leftovers, and cannot guarantee a storage, memory, recovery-time or pause bound.
- `CheckpointStore::compact_to` pauses source mutations, validates its trusted checkpoint and complete bounded suffix, then streams live keys into a new private store using the same synchronized record-group limits. It validates the target log and witness, compares its ordered key/value digest and count against the source, and emits a verified checkpoint inside the copy. The returned checkpoint digest must be protected separately. The compacted history starts with the current live keys, so its historical key-count peak is reset to that count. Existing readers may continue; the source remains unchanged, later source writes are absent from the copy, and switching applications is manual. A parent-directory sync failure after publication has an uncertain outcome. This avoids materializing complete source or target indexes during the operation but does not bound total process memory, provide in-place compaction, or erase old records from the source or backups.
- Backup, restore, format upgrade, explicit checkpoint creation, live checkpoint rollover and both separate-copy compactors synchronize the published destination directory and every resolved ancestor bottom-up before reporting success. If any synchronization fails after publication, the destination may exist and the operation reports an uncertain outcome; the source remains available subject to its normal health rules. This synchronizes resolved paths, not the containing directories of symlink aliases. Alias creation is caller-owned: before depending on an alias after a crash, the caller must synchronize its containing directory and its ancestors, including any other aliases in the path, or use a canonical path. Some managed paths are stored only after resolution, and the engine cannot discover other aliases. Paths and aliases must not be changed by uncooperative processes during these operations. It assumes cooperating access to a trusted path and a filesystem and device that honor the required sync operations. It is not evidence of physical power-loss safety. Tests inject errors at each ancestor for these publication paths.
- `OnlineStore::cleanup_retired_staging` removes only new retired markers tied to this store’s witnessed log identity, which were created after a verified synchronized handoff. Under the current store’s maintenance and writer barriers and an exclusive cooperative parent lock, it verifies the complete current log against a bounded snapshot before deleting anything. It skips malformed markers, unexpected or symlink contents and locked retired stores; a failed verification leaves that stage intact. Known files are removed in log, witness, lock order, then the retired and staging directories are synchronized and removed. A process interruption can be retried. An error can follow partial cleanup and the parent is synchronized where possible. Generic cleanup skips these new markers. The optional `start_reclamation_worker_with_retired_cleanup` checks them before compaction, pauses compaction while any are skipped, exposes counters, retries only recognized pre-cleanup lock conflicts and stops on other errors. Named previous copies, legacy generic stages and other log identities are not removed. Malformed retired markers anywhere in the parent can block compaction for inspection, and an unused previous path is required to start the worker. Verification scans the full log and can block writes; limits may reject it. Markers and paths require a trusted, cooperating parent: CRC and identifiers do not provide authorization. This is not secure erasure, a disk or memory quota, an independent backup, or proof of physical power-loss behavior.
- Backup, restore, upgrade, checkpoint and compaction reserve the `.emda-stage-v1-` destination-path namespace. New staging operations synchronize a versioned ownership marker and its parent directory before creating a payload, hold a nonblocking shared advisory lock on the destination parent during staging and publication, and release it after the operation finishes. A conflicting cleanup returns `WouldBlock`; if the lock cannot be acquired, a new staging operation fails before creating its marker. The explicit `cleanup_abandoned_staging` API takes the parent lock exclusively, recognizes matching generic markers and payload types, skips new retired markers, symlink payloads and unknown markers, and synchronizes the directory after attempted cleanup. Deletion may be partial if it reports an error. This requires a trusted directory and cooperating processes; it is not safe against concurrent external replacement, adversarial directories, unsupported locks, or uncooperative software. Cleanup is not secure erasure. It is explicit except for the automatic checkpoint paths described below. Older unmarked `.db-*` files and directories are not removed and may contain plaintext data. Forked children can temporarily retain a lock after a killed parent; a normally dropped staging guard explicitly unlocks even if a descriptor was duplicated. Continuing an inherited staging operation after `fork` is unsupported.
- A `Store`, `CheckpointStore`, `CheckpointView`, `RecoveredCheckpointView` or borrowed snapshot may be used in its owning process. After `fork`, the child must not use the inherited object; it should `exec` or exit without running inherited database operations. On tested Linux, the long-lived advisory lock descriptor is inherited until `exec` or close, so dropping the original object can leave the store temporarily locked by a pre-exec child or another duplicated descriptor. The descriptor is close-on-exec for the tested ordinary process-spawn path; an independently executed contender is excluded while the original owner is alive. Manually changing descriptor flags, unlocking or passing inherited descriptors to other processes is unsupported. These are cooperative filesystem locks, not tenant isolation or fencing against noncooperating programs.
- Process-kill tests stop these five operations after staging and after publication before parent synchronization, check that cleanup is blocked while they run, and validate the source or published copy and cleanup on the running OS. Marker and cleanup directory-sync failures are also injected. These tests do not establish which entries survive physical power loss.
- On Linux, consuming `Store::compact_and_replace` makes and verifies a compacted sibling before atomically exchanging it with the source directory. Both store locks remain held through exchange and parent-ancestry synchronization. After lock acquisition, cooperating current-version ordinary stores, checkpoint stores and checkpoint views check that the opened lock descriptor still identifies the lock at the requested path, preventing a stale descriptor from authorizing access to the newly exchanged log. Resource limits are reapplied to the returned store. The previous complete store remains at the sibling path; it may contain historical plaintext and must be retained or removed deliberately. The operation rejects unknown source files, symlinks, managed checkpoint metadata, non-sibling destinations and existing destination paths. It blocks access, invalidates external checkpoints and is not online compaction, total-memory control, secure erasure or a physical power-loss guarantee. After exchange or directory-sync failure the publication outcome is uncertain; both paths must be inspected and reopened. The protocol assumes a trusted directory, current-version cooperating clients, supported atomic exchange and correct filesystem/device synchronization. An older opener without lock-identity checking can race and is not a cooperating client for this operation. Injected and process-kill tests are not power-loss tests.
- On Linux, consuming `CheckpointStore::compact_and_replace` streams and verifies a compacted sibling and its checkpoint, then exchanges the sibling with the live directory while holding both locks and synchronizing the parent ancestry. It preserves the per-open suffix and log limits, managed selection and automatic-checkpoint enabled/disabled state. A managed candidate's selection names the checkpoint at its final source path before exchange; if interrupted before exchange, the candidate sibling may require ordinary full-log recovery. After exchange the returned checkpoint digest identifies the new `index.checkpoint`; unmanaged callers must retain it separately. The previous full log is retained, but old managed selections can contain absolute paths that no longer identify their old checkpoint, so use ordinary full-log recovery or explicitly rebuild selection when needed. Unknown source files and symlinks are rejected. After exchange or parent-sync failure the published outcome is uncertain; inspect and reopen both paths. This blocking operation assumes trusted paths, current cooperating lock-identity-aware clients and correct filesystem/device synchronization. It is not online reclamation, secure erasure, a total-memory or bounded-recovery guarantee, or evidence of physical power-loss behavior. Injected failures, process kills and document/index recovery are tested on the running OS.
- The experimental `DocumentDatabase` shares its underlying transaction and DB02 commit with unreserved raw key operations invoked through the same `DocumentTransaction`. Document, index and raw mutations commit atomically under that store’s documented synchronization and isolation assumptions. Failed document mutations abort the document transaction even if caught. The [document model](DOCUMENT_MODEL.md) specifies limits and its trusted reserved key prefix. SQL does not exist and cross-database transactions are not provided.

### Corruption and format compatibility

- Header and record CRC32 checks detect some accidental corruption on reopen; current value bytes are checked on read. CRC32 is not authentication, cannot detect every possible error, and cannot reconstruct damaged data. A detected checksum failure is reported; no automatic repair from replicas or backups exists. Backups add a length and SHA-256 digest and revalidate records, but are unencrypted, unauthenticated, and not proof of protection against all storage failures.
- Explicit `checkpoint_to` verifies the complete source log and live index, writes a checksummed index file without replacing an existing path, synchronizes it, and returns its SHA-256 digest only after parent-directory synchronization. A publication sync failure has an unknown outcome. `open_with_checkpoint` requires that digest from separately trusted metadata, verifies the checkpoint file, codec version, recorded historical key peak, witness boundary and complete covered log-prefix SHA-256, then replays and validates the tail. Optional log/key limits can be applied on open. A rejected checkpoint never authorizes partial recovery; ordinary `open` replays the full log without it. Checkpoints contain plaintext keys, are not independent backups, and are not authenticated if an attacker can replace both checkpoint and trusted digest. Prefix hashing still reads all covered log bytes and the index is loaded into memory; neither recovery time nor process memory is bounded by the checkpoint.
- `CheckpointView` provides a bounded-memory, historical read-only checkpoint view under a shared advisory lock. Cooperating writable stores cannot coexist with it; multiple views can. Opening verifies the trusted digest and full covered log prefix, and each subsequent index-block read is checked against a digest held in the view. Value reads verify their existing CRC. It does not replay or validate bytes after the checkpoint and can show older data; `has_log_tail` reports only the presence of such bytes at open, including potentially incomplete or corrupt records. It is not current recovery. At most 131,072 index blocks are indexed per view, and each block read uses at most a 32 KiB index buffer, in addition to the bounded result or value. Searches may read several blocks, especially when keys share long prefixes, and scans may read more. Aggregate memory across simultaneous views or calls is not limited. The separately trusted digest, cooperative-locking assumptions and complete prefix-hashing costs above apply equally here.
- `RecoveredCheckpointView` uses the same independently trusted checkpoint and shared lock, then validates and replays every record from the checkpoint boundary through the witnessed log boundary into an in-memory overlay. Point reads and ordered scans merge that overlay, including tombstones, with the verified checkpoint blocks. It rejects any bytes beyond the witness, including a complete unacknowledged tail; a writable store must adopt a valid complete tail before the view can open. Default hard limits are 64 MiB of raw suffix, 16,384 distinct touched keys and 4 MiB of their key bytes, including deleted keys; callers can choose lower limits. `open_with_options` also accepts checkpoint file/block limits and an optional whole-log byte cap, checked before checkpoint verification and again before publishing its base view. `CheckpointView::open_with_recovery_limits` provides the same checkpoint and log controls for a historical view. The cap includes all suffix bytes and must be reapplied on each open. Limits are checked before a partial view is returned. They do not cover allocator overhead, record buffers, returned values, simultaneous views or total process memory. Opening an accepted checkpoint still hashes the full covered log prefix, and neither recovery time nor aggregate memory is bounded. Later checkpoint block reads and selected values retain their checksums; noncooperating external modification is outside the locking model. The view cannot coexist with a cooperating writer and is not a writable disk-backed index.
- `CheckpointStore` uses the verified checkpoint and bounded recovered suffix as a writable base under an exclusive advisory store lock. Reads and mutations synchronize through one process-local lock. Bulk reads capture one state, preserve input order and duplicates, and enforce the same 1,024-key and 32 MiB response limits as the ordinary store; they are not transactions. Single-key changes, conditional updates, increments and blind atomic DB02 batches append in order, synchronize using the existing V2/V3 witness protocol, and publish their overlay changes only after successful synchronization. A batch is observed before or after its complete publication. Before append, admission checks suffix bytes and distinct touched keys/key bytes, including tombstones; callers may choose lower limits than the recovered view hard caps. A rejection leaves the log unchanged. After append starts, an error or panic makes its outcome uncertain and prevents further operations on that instance. Reopening validates the trusted checkpoint, the witnessed boundary and the complete suffix, subject to its limits; a complete unacknowledged tail is synchronized and its witness advanced before the instance is returned. An incomplete tail fails closed without truncation. A synchronization or witness error during recovery has an uncertain outcome. Tests inject partial appends and V2 witness writes, V3 metadata write/sync failures and panics, and kill a process after acknowledgement; these tests do not establish power-loss safety. Explicit `CheckpointStore::checkpoint_to` pauses mutations, revalidates the separately trusted base checkpoint and its covered log prefix, replays the witnessed suffix, checks the resulting overlay and historical key-count peak, and streams a new checkpoint. It validates the output before publishing it, synchronizes the staging file and parent directory, and returns a digest that must be protected separately. A publication sync error leaves the new path uncertain. `checkpoint_to` leaves the current overlay in place. `rollover_to` additionally opens and verifies the new checkpoint under the same exclusive lock, then swaps views and clears the overlay without a lock gap; both reads and writes wait during the operation. If publication succeeds but the new view cannot be opened, the old view stays active and the new path may exist. The caller must persist the returned digest and choose the checkpoint on the next open; this selection is not recorded automatically. Keep the store directory accessible at its resolved path during a live switch. If the new digest is lost, an older trusted checkpoint may be usable within its suffix limits; ordinary full-log recovery remains the fallback. The operation uses bounded block buffers, a second bounded suffix overlay and, during handoff, two checkpoint block directories; these limits are not a total process-memory guarantee. The full prefix is still hashed. `CheckpointStore::backup` holds a read barrier that blocks mutations while copying, verifying and publishing a full-log backup; other readers may proceed. Backup, restore and format upgrade validate every record through the streaming parser without constructing a full key index, but record and batch buffers, returned values and other allocations remain outside a total-memory quota. The backup remains plaintext, unauthenticated and dependent on independent retention and restore checks. This path has no group commit or total-memory quota; background checkpoint scheduling requires the separately started worker described below. A suffix exceeding the configured caps needs a newer checkpoint or ordinary full-index recovery.
- `CheckpointStore::compare_exchange_batch` checks up to 1,024 point-value conditions under its exclusive in-process write lock and applies one atomic DB02 batch only when every condition matches. `None` denotes an absent key; duplicate conditions are checked independently. Condition keys and expected values are limited to 32 MiB in total. Mismatches and validation failures append nothing; an append or synchronization error has an unknown outcome and poisons the instance. Conditions compare current values and can miss an ABA change, and no range or phantom validation is provided. This primitive is not a general read-modify-write transaction callback.
- A historical `CheckpointView` can be opened with explicit checkpoint file-byte and block-directory-entry caps. `CheckpointStore::open_with_options` and `open_managed_with_options` combine these caps with the existing suffix and optional log-length limits. A file-size rejection occurs before checkpoint parsing or log-tail adoption; a block-count rejection occurs while privately verifying the checkpoint, before the view is returned. Rollover and compact-and-replace apply the same caps to their candidate view. A rollover rejected after checkpoint publication retains the old view and may leave the new file; an automatic rollover rejected before append keeps the old selection and does not submit that write. A failed compaction candidate can leave its separate copy. These per-open caps are not persisted, do not bound checkpoint creation files before adoption, concurrent or temporary allocations, allocator overhead, total process/project memory or elapsed time, and do not skip full covered-log verification. An optional log cap can separately bound the file size admitted during checkpoint-store open.
- `CheckpointStore::rollover_managed` provides opt-in persistent selection under the same exclusive store lock. It verifies and durably publishes a new checkpoint, verifies the new view, writes and synchronizes a versioned selection in the store directory, atomically renames it over `checkpoint.selection`, and synchronizes that directory and its ancestors before switching the live view or resuming reads and writes. The checkpoint directory and its ancestors are synchronized before selection publication. A checkpoint-stage failure keeps the previous view; if selection publication fails or panics, the writer becomes unusable because the rename may have occurred. `open_managed` acquires the store lock, rejects missing, malformed, unknown-version or symlink selections, verifies the referenced checkpoint and complete covered log prefix, and synchronizes the visible selection and store directory ancestry before accepting writes; complete unacknowledged tails are subject to the existing validation and limits. If the first selection was never published, explicit recovery with the prior trusted checkpoint or ordinary full-log recovery is required. The selection records an absolute path; moving or deleting the checkpoint breaks reopening. Its SHA-256 is only an accidental-corruption check: the store directory and selection must be trusted and protected separately from checkpoint contents, and an attacker who can replace both can forge them. External modification or noncooperating access is unsupported. Once a selection exists, explicit `CheckpointStore::open` and unmanaged live rollover reject it. Ordinary `Store` and older engine revisions do not enforce this selection and may grow a suffix beyond managed limits. Backup/restore preserves the log but not this selection or its checkpoint. This is not automatic scheduling, in-place compaction, log reclamation, a memory quota or a physical power-loss guarantee. Injected pre/post-rename errors and panics, competing writer barriers, corruption, and process kills before/after rename are tested on the running OS.
- `CheckpointStore::enable_automatic_checkpoints` persistently opts a managed store into on-demand rollover. Before an otherwise valid mutation would exceed a suffix byte, distinct-key or key-byte limit, the writer lock remains held while an inactive, engine-owned slot is checked and reclaimed, a new checkpoint is streamed, verified and synchronized, and a managed selection is atomically published and synchronized. The pending mutation is appended only after successful handoff. If the mutation cannot fit even an empty suffix, or would exceed the whole-log cap, it is rejected before creating a checkpoint. Rollover itself does not advance the transaction generation; checkpoint locations and the source log remain immutable, so transaction and snapshot observations remain valid. Old snapshot checkpoint descriptors can outlive slot unlinking on Unix, retaining their captured data and potentially retaining disk blocks. Two named slots bound the number of linked automatic checkpoints, not total disk use or open snapshot resources. An error or panic during selection or configuration publication can leave an uncertain visible state and poisons the writer until reopening. Checkpoint-slot failures before selection publication leave the old selection active; the pending mutation was not appended. `disable_automatic_checkpoints` atomically persists the disabled state and retains slot files. On managed open, recognized abandoned stages in the store and automatic root are cleaned only under cooperative directory locks; unknown entries, symlink slots and invalid ownership markers are never removed. The reserved `.emda-auto-checkpoints-v1` directory and managed selection must be protected as trusted metadata. This is a synchronous, on-demand mechanism, not a background scheduler, online log compaction, a total resource quota, or a bounded recovery-time guarantee. Process-kill and injected-failure tests establish behavior on the running OS, not physical power-loss safety.
- `CheckpointStore::start_checkpoint_worker` optionally starts one process-local worker per open, managed store after automatic checkpointing is enabled. It checks after its configured interval or a coalesced request; when automatic checkpointing is enabled and the suffix meets the threshold, it performs the same synchronized, lock-held automatic rollover described above. Disabling automatic checkpoints makes checks skip until re-enabled. An I/O error stops the worker and appears in its status; a panic is caught and reported, while the store's own poison/unknown-outcome rules remain in force. A worker retains an `Arc` to its store, so stop it before consuming the store for compaction. Stop and drop wake and join the worker, but an in-flight lock wait or I/O is not interrupted and can delay shutdown indefinitely. The worker is not persisted or started by opening a store. It does not reclaim the live log, guarantee total resource limits or bounded recovery, provide scale-to-zero project lifecycle, or establish physical power-loss behavior. Tests cover concurrent start admission, periodic and requested checks, disable/re-enable, snapshots, transactions, errors, panics and shutdown while a check is blocked.
- `CheckpointStore::rebuild_managed_selection` explicitly recovers an existing witnessed store using the ordinary full-log replay and in-memory index, under its exclusive advisory store lock. It rejects invalid, symlink or unknown-version selection metadata, builds a non-overwriting checkpoint, synchronizes its directory ancestry, opens it as a managed-compatible view under the same lock, and atomically publishes and synchronizes a fresh selection and its directory ancestry. It does not need the previous checkpoint to be accessible and can repair a suffix that exceeds the managed reader's limits. If checkpoint publication fails, the old selection is untouched; an error or panic during selection publication can leave either selection visible. Reopen and verify the visible selection, or use full-log recovery when no selection is present. `rebuild_managed_selection_with_limits` optionally applies a whole-log byte cap, historical live-key count cap and historical live-key byte cap while replaying every state, before a new checkpoint or selection is published. The caps are per-call and exclude values, index overhead and other allocations. The method releases its lock before returning; callers must coordinate other writers before reopening. It loads the complete in-memory index, may allocate an additional verification index, hashes the full log, and provides no bound on time or total memory. It is not log compaction or automatic recovery. Fault, lock-exclusion and process-kill tests cover these boundaries only on the running OS.
- `CheckpointStore::open_with_resource_limits` accepts an optional per-open cap on the entire log file, including its header, replaced records and tombstones. It rejects an oversized log before suffix replay or adoption and rejects a mutation before append if its encoded record would exceed the cap. Its write lock serializes admission and commit, including across checkpoint rollover, which does not reclaim log bytes. The cap is not persisted and excludes checkpoint files, backups, memory and total project storage.
- Single-key records use the experimental `DB01` marker; atomic batches use the `DB02` marker and contain checksummed `DB01` records. Older revisions cannot reopen logs containing `DB02`. On Linux filesystems supporting user xattrs, new stores have a checksummed `EMDALOG3` header, a metadata witness, and an immutable `commit.state` identity anchor. Unsupported xattr operations during creation fall back to V2 (`EMDALOG2` and its changing `commit.state` witness); other initialization errors propagate. Existing V2 stores retain their two-sync protocol and existing unwrapped `DB01` logs retain their earlier recovery limitations. Opening V3 never falls back if required metadata is missing or unsupported. Backups retain the log format and length/digest. Restore recreates and synchronizes the format's witness, except that a validated zero-byte legacy log becomes a new witnessed empty store with a new identity; this is an intentional restored-format change. V3 restore currently requires Linux with supported xattrs. Ordinary file-copy tools must preserve xattrs, identity files and log bytes; use the engine backup/restore API for verified copies. Unknown or invalid markers are rejected. Older engines cannot open the new header. The software version and on-disk format version are separate; the current prototype has no stable backward-compatibility or downgrade promise. See [VERSIONING.md](VERSIONING.md).

- Both writable stores can adjust and inspect their process-local aggregate transaction reservation limit. Admission and reconfiguration share one mutex; a limit above 64 MiB is invalid, while a reduction below current reservations returns `WouldBlock` with no change. A zero limit rejects nonempty staging; checkpoint read-set observations also consume this budget. Reservations are released after commit, failure, cancellation or unwind. Supported blocking and guarded online compaction preserve the setting across handoff, including changes made during the initial online copy; reopening resets it. Direct writes, snapshots, allocation overhead, other stores and total process/project resource use are excluded. The setting is not persistent isolation, an OS resource limit, or a connection quota.
- Both writable stores also admit at most 64 active transactions per open instance, including FIFO waiters, callbacks and commits. A configurable lower limit and the active count share the transaction-budget mutex. At the limit, admission returns `WouldBlock` before running the callback or submitting a write; lowering the limit below the active count likewise fails without changing it. Zero rejects all new transactions. Admission is released after completion, cancellation, callback error or unwind; it is retained until any started commit has finished. Supported compaction handoffs preserve the configured limit, while reopen resets it. Direct writes, independent snapshots, waiting caller threads and other store instances are excluded. This is not a total-memory, CPU, connection, project or fairness guarantee.

## Proposed contract for future design

The following are acceptance targets, not existing guarantees. Exact algorithms and API behavior must be specified, reviewed, and tested before release.

1. **Durability:** Define the exact acknowledgement point, storage and filesystem assumptions, crash and power-failure model, partial I/O behavior, and how an unknown result is reported. Acknowledged writes must survive the documented failures under those assumptions; failed requests must never be silently treated as definitely absent. Backups and restores require separate verification.
2. **Transaction isolation:** Document every supported level and its anomalies. The prototype provides an optimistic serializable transaction API within one open store; broader production semantics and additional isolation levels require further validation and design. If offered, serializable transactions must prevent dirty reads, non-repeatable reads, phantoms, and write skew. Serializability alone must not be described as a real-time ordering guarantee.
3. **Cross-interface atomicity:** Within a single supported transaction and database, key-value, document, and SQL operations must use the same commit and isolation machinery. Record and index updates commit together or not at all. Cross-database, cross-project, external service, and distributed transaction behavior must be specified separately; no guarantee is assumed.
4. **Ordering and consistency:** Define operation and commit order, read-your-writes, concurrent conflict behavior, and what a client may observe during and after failure. For streams and replication, define the scope of ordering, acknowledgement, retry, and delivery semantics explicitly.
5. **Snapshots and garbage collection:** Define snapshot visibility, lifetime, resource limits, cancellation/expiry behavior, and how retained versions are reclaimed. Compaction and garbage collection must not invalidate an active supported snapshot or remove data needed for recovery. Any timeout must be explicit rather than silently changing a result.
6. **Corruption:** Specify which corruption is detected, when the engine stops safely, and how recovery from a verified backup or replica works. Checksums alone must never be presented as data recovery.
7. **Formats:** Version record, index, checkpoint, snapshot, API, and protocol formats independently where appropriate. Define supported upgrades, downgrades, migration and rollback, and fail safely for unknown versions. Compatibility claims require tests using persistent fixtures from the supported versions.
8. **Sleep and wake:** Stopping an idle project worker must not weaken this contract. Define draining of in-flight operations, snapshots and background jobs, durable stored data, ownership fencing, bounded wake-up retries, and recovery errors. No scale-to-zero behavior is implemented today; see [SCALE_TO_ZERO.md](SCALE_TO_ZERO.md).
9. **Project boundaries:** Transactions, caches, indexes, snapshots, logs, streams, and recovery must not access another project's data without explicit authorization. Enforce and test this in the service, engine, and storage layers; see [PROJECT_ISOLATION.md](PROJECT_ISOLATION.md). No tenant security is implemented today.

## Evidence required before a guarantee is advertised

Deterministic partial-append including every byte of a vectored group, partial witness writes at every byte, witness update/sync errors, ordering of log and witness syncs, directory-creation ancestor-sync errors, short-read errors including during buffered replay, record-boundary truncation and byte-by-byte log/witness corruption checks, a torn-witness crash model, controlled overlapping reads and writes, reservation failure and panic tests, grouped-sync failure and panic tests, delayed-handoff and queue-limit tests, short model-checked single- and multi-key histories of independent operations, 2,048 short mixed transaction/batch/read histories checked against a serial model with reopening after each history, process termination after acknowledged concurrent writes, persistent legacy, V2 and V3 fixtures, legacy upgrade, backup/restore checks, and a local cross-filesystem restore drill exist. Backup checks include every truncation and single-byte mutation position of a small fixture, competing restores to one destination, and an existing symlink destination. The V3 path additionally has every-byte record/witness corruption, every shorter log length, all prefixes of an interrupted append crossed with torn witness prefixes, log-only rollback, delayed-sync publication, metadata failure/panic, upgrade, and restored-boundary tests. Coverage-guided fuzz campaigns exercise malformed recovery input. Further work must exercise interruption at every initialization/commit/backup boundary, the remaining directory-sync paths and actual power-loss models, off-host restore drills, broader model-based concurrent histories, and additional persistent compatibility fixtures. A process kill alone is insufficient for power-loss claims. Snapshot, compaction, index, and cross-interface tests must be added as those features are implemented. Report the assumptions and any untested failure cases alongside the results.
