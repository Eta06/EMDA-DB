# Storage and transaction contract

This document separates **current prototype behavior** from **design targets that are not implemented**. It is not a production durability, isolation, or recovery guarantee. The same core contract must eventually govern key-value, document, and SQL interfaces when they operate on the same database. Each new interface must state its scope and any restrictions before it is shipped.

## Non-negotiable optimization rule

No performance optimization is accepted if it violates the durability, isolation, or recovery guarantees in force for the feature. This rule also protects the prototype's documented behavior; the absence of a production guarantee is not permission to weaken its write synchronization, coordination, corruption detection, or recovery behavior. This applies to zero-copy access, caching, memory mapping, async I/O, compression, group commit, SIMD, assembly, and adaptive storage alike. The faster path must preserve the same contract, fail safely, and pass the same correctness and fault tests. Benchmarks compare equivalent guarantees; disabling synchronization or weakening isolation to obtain a better number does not meet this rule.

## Current prototype: one store in one process

### Successful writes and ordering

- Each `put` or `delete` appends one checksummed record and returns success only after the log data and in-memory index update complete. V2 stores update and synchronize an independent commit-witness file after synchronizing the log. V3 stores append records, update a checksummed boundary in the log inode's `user.db.commit.v3` extended attribute, then perform one full `fsync` covering both file data and metadata before publishing the index or acknowledging the write. `fdatasync` is insufficient for this V3 metadata guarantee. A separate immutable identity anchor is synchronized at creation and checked during writes and backups. Legacy stores synchronize the log only and retain the limitations below. One log leader appends records in queue order. Concurrent single-key mutations can share a synchronization; grouping does not make them an atomic multi-key transaction. Deleting a missing key writes a deletion record. Deleted and superseded values remain in the append-only log and full-log backups; delete does not perform secure erasure.
- Readers share an index read lock to select a value's location and can observe the previous indexed value while a writer synchronizes; the index update is exclusive. Once selected, the immutable log location is read and verified without holding the index lock. A read beginning after a successful write returns that value unless a later mutation replaces or deletes it, or an I/O/corruption error occurs. An overlapping read can select either the old or the new location, including completing after a later write.
- Single-key mutations concern one key. `write_batch` encodes up to 1,024 ordered puts/deletes and 16 MiB of encoded payload in one checksummed `DB02` log record, synchronizes it before acknowledgement, and publishes every index update under one lock. A `get_many` or snapshot sees either the index before or after the batch. Incomplete or corrupt batches fail closed; a complete unacknowledged batch can be adopted in its entirety on recovery. Batch errors after append have an unknown outcome and poison the store. Batches require V2/V3 witnesses and block other writers during commit; older readers cannot parse `DB02`. When a live-key limit is configured, each ordered intermediate batch state must stay within it, both at admission and during replay. A batch is a blind atomic write, not a read-modify-write transaction. `compare_exchange` serializes a single-key comparison and mutation against other writers; a mismatch does not write, and a matching mutation uses the ordinary sync-before-acknowledgement path. It compares values rather than versions and does not detect ABA changes. `increment_i64` likewise serializes against writers; it treats a missing key as zero and stores a checked, eight-byte little-endian signed integer. Invalid encoding and overflow do not write. Both conditional operations currently exclude all concurrent writers, even on other keys. `scan` captures ordered key/immutable-value locations under the index lock and reads those values after releasing it; each page is limited to 1,024 entries and 32 MiB of key/value bytes. Different pages can observe concurrent updates and are not a transaction snapshot. `get_many` captures its selected locations under one index lock, preserving request order and duplicates; it rejects requests of more than 1,024 keys or 32 MiB of key/value bytes and returns no partial result on error. Deleted values already selected by an overlapping scan or bulk read can still be returned. There is no user-visible sequence number or change stream. Reads return owned bytes; the engine does not offer zero-copy reads.
- An OS advisory lock prevents cooperating processes from opening the same store at once. This is not a security boundary or a guarantee against processes that ignore the lock.
- The commit coordinator reserves capacity before preparing records and limits reserved and queued encoded sizes awaiting completion to 64 MiB and 1,024 records, with up to 64 records per sync. Preparation happens outside the queue lock; overlapping writes can enter the queue in a different order from their reservations. Writers wait when admission is full. This bounds encoded bytes, not total process memory or the number of caller threads; there is no timeout or service-level admission policy. Backups wait for in-flight writes and exclude new writes while the log is copied.
- `open_with_log_limit` applies an optional per-open maximum log-file length. Before entering group commit, each mutation reserves the complete encoded record length against a counter that includes the initial log and all committed or in-flight reservations. A request is rejected before append if the cap cannot accommodate it; pending reservations may temporarily cause rejection even if an earlier request later fails before append. Pre-append errors release their reservations. I/O errors after a permitted append have an unknown outcome and poison the instance; reopening checks the actual log length before replay and reconstructs the counter. Independent writes may share a sync. The cap counts headers, replaced values and tombstones; even a delete can be rejected. It is not persisted, and opening can initialize a new store before the length is checked. Other files, memory, external modification and total project storage are outside this limit. Normal `open` has no cap.
- `open_with_limits` can also limit the number of live keys for that open instance. New keys are rejected once the cap is reached; updating existing keys and deleting keys remains allowed if any log-length limit also permits the record. Membership-changing operations serialize for admission so concurrent operations cannot oversubscribe the key count. Updates to already-present keys hold a shared membership barrier through acknowledgement and may share a sync; inserts, deletes and compound mutations wait for that barrier. Recovery checks the count before inserting each new key and fails closed if any historical log prefix exceeds the limit, even if later deletes would reduce the final count. Such a failure does not modify the log or advance the commit witness. The setting is not persistent, and the count does not establish a byte or process-memory bound. Ordinary `open` has no limits.
- `open_with_resource_limits` additionally accepts a per-open limit for the combined lengths of currently live keys. A new key is rejected before append if it would exceed the limit; updates do not add key bytes and successful deletes free them. Under the exclusive membership barrier, the live-byte counter advances only after a successful membership-changing commit; already-present key updates may share synchronization and cannot change the counter. A failed commit keeps the store unusable until reopening reconstructs the counter. Ordered batches check every intermediate operation, and transactions check their encoded delete-before-put order. Full recovery enforces the cap across all historical prefixes and every ordered batch operation before adopting an unacknowledged tail. A historical peak can prevent opening even if the final live set fits; separate-copy compaction may reduce it. The cap must be supplied again on every open and is unavailable through checkpoint recovery, whose current format does not record the historical live-byte peak. It excludes index allocation overhead, values, snapshots, log and other files, other stores and total process memory; it is not a persistent project quota or security boundary.

### Crash, power failure, and uncertain outcomes

- After a successful return, the prototype has requested synchronization of the appended log data and, for a new-format store, the commit witness. The intended process-crash behavior depends on the filesystem and device honoring synchronization, including persistence of xattrs by a full inode `fsync` for V3. Before that sync completes, V3 data and boundary metadata can reach storage in either order; a boundary ahead of valid data fails closed. A DB02 batch is one atomic record; grouping independently submitted records does not make them one transaction. V2 retains its original ordered two-file synchronization. The tests cover reopening after a killed process and injected I/O faults, not every crash point or hardware failure.
- If append or synchronization returns an error, some or all bytes may already have been written. Unacknowledged mutations in the affected group and queue fail with **unknown** outcomes, and this store instance refuses further reads and writes until reopened. A complete but unacknowledged record can appear after recovery. A panic in the commit leader also fails the store and wakes waiting writers. Completed requests are signaled individually, and queued requests periodically recheck leadership; scheduling and wait times remain unbounded. There is no request-id or retry-deduplication guarantee.
- On reopen, the engine scans the log in append order using a bounded read buffer, verifies every record, and refuses to open an incomplete final record, invalid header, or checksum error without truncating the log. New-format stores have a checksummed witness tied to their log identity. If the intact witness records an offset missing from the log, including truncation exactly at a record boundary, opening fails. A missing, incomplete, corrupt, wrong-identity, or non-boundary witness also fails closed. A complete valid tail beyond the witness may be an unacknowledged write: recovery synchronizes that log and advances the witness before returning. An incomplete tail is never silently truncated. A failed witness update has an unknown outcome and the open instance refuses further operations.
- The log and witness share a filesystem and are not independent backups or replicas. V3 keeps its boundary outside the log byte stream, so truncation or rollback of just log bytes is still detected when it removes the witnessed boundary; missing metadata also fails closed. Rollback of the data and witness together (including a V3 inode or filesystem snapshot), rollback of the witness alone to an older valid value, equal-length replacement with valid earlier records, checksum collisions, or storage that violates synchronization assumptions can escape detection. Neither format authenticates record history or protects against an adversarial filesystem. Corrupt witnesses fail closed; they do not reconstruct damaged data. Legacy `DB01` logs have no witness, so loss at a complete record boundary can still go undetected. `Store::upgrade_format` creates a verified non-overwriting copy in the current format; `Store::upgrade_legacy` remains a legacy-only wrapper. Conversion establishes a witness at the data currently present; it cannot discover loss that occurred before the upgrade. Independent verified backups remain necessary.
- Store initialization synchronizes the path and its ancestor directories, but no universal power-loss guarantee is established: underlying filesystem and device behavior matters, and actual power-cut testing is absent. Full-log backup/restore is experimental and depends on supported filesystem operations; independent backups and restore drills are still necessary. Do not use this prototype for important production data.

### Isolation, snapshots, and interfaces

- `Store::transaction` provides an experimental optimistic serializable transaction within one open store for point and ordered range reads and staged puts/deletes. It captures an index snapshot and an in-process generation under the same read lock. Transactional reads see that snapshot plus staged writes. Before commit it takes the exclusive writer barrier and rejects with `WouldBlock` if any mutation has published since the snapshot, including a write to an unrelated key or an ABA change. Thus a successful transaction can be serialized at its validation/commit point relative to other transactions and ordinary store mutations, subject to the stated storage assumptions. Conflicts never append the staged writes; there is no automatic retry. A callback error or panic discards staged writes; external side effects are not rolled back. A successful write transaction commits one DB02 record, synchronizes before returning, and requires a witnessed V2/V3 store. Commit I/O errors have an unknown outcome and poison the store. Read-only transactions do not append. Transactions use the read-snapshot limits and aggregate snapshot budget, so stores over 16,384 keys or 4 MiB of key bytes cannot currently start one; staged writes are limited to 1,024 keys and 16 MiB of encoded operations. The generation is process-local and resets on reopen; snapshots and transactions cannot outlive the store. There are no distributed or cross-project transactions, bounded-completion or fairness guarantees, automatic retry or external side-effect rollback, or compatibility claims for SQL/document interfaces. This is a prototype and not a production isolation guarantee.
- `CheckpointStore::transaction` captures a process-local generation without copying the index. Each point or range read holds the state read lock while checking that generation and reading the verified checkpoint plus suffix, then merges staged changes. Final validation and any atomic DB02 commit hold the state write lock. Every successful mutation advances the generation; generation exhaustion rejects a write before append, while checkpoint rollover alone does not change it. Thus an intervening mutation, including unrelated writes and ABA changes, makes subsequent reads and final validation fail with `WouldBlock`. Even a callback that catches a conflict cannot commit its staged changes. Successful transactions serialize at final validation/commit; read-only transactions append nothing. Callback errors and panics discard staged changes, but external effects are not rolled back and callbacks are not automatically retried. Writes are synchronized and have the same unknown-outcome rules as other checkpoint-store writes. Staging uses the 1,024-key and 16 MiB batch limits and a 64 MiB encoded-record budget across concurrent transactions on this open store; response copies, allocations, checkpoint buffers and commit encoding are excluded. This path has no global fairness, active-transaction count or total-memory guarantee.
- `CheckpointStore::transaction_with_read_set` records immutable point locations and complete requested scan ranges without copying the full index. When the generation changes, it revalidates prior observations under the state read lock before returning another read or accepting a staged write; it also validates under the state write lock before commit. This prevents callbacks from observing a fractured pair across an atomic update. A successful callback's observations match its commit state, even when unrelated writes occurred between reads. A changed observation returns a sticky conflict; changing and restoring a present value has a different location, while an insertion and deletion never observed by the transaction can leave the same absence or range. Each scan records all entries in its requested bounds, including entries beyond a limited page, so phantoms and changes anywhere in that range conflict. Dependencies are capped at 2,048 distinct points and ranges, 2 MiB of retained keys and bounds, and 65,536 total point/range items per transaction. Retained key bytes and fixed point/range metadata reserve from the same 64 MiB per-store budget as staged records; allocator/map overhead, vector capacity slack, response copies and validation buffers are excluded. During capture, reservations grow in quanta, potentially reserving extra space temporarily; unused space is released before returning a page. Near the limit, exact reservations are attempted. Duplicate ranges share an observation. Capture or admission failure returns before an untracked page or point value is returned. Capturing and revalidating large ranges can be expensive and hold a state lock while reading checkpoint blocks; the per-validation item cap does not bound total callback work. Independent store reads and external effects are outside the transaction. `transaction_with_read_set_fifo` uses the same validator with FIFO callback and commit admission.
- `CheckpointStore::transaction_with_fifo` uses the same conservative validation but joins a FIFO queue before beginning its callback. The queue accepts at most 16 participating transactions and releases a turn after the state write guard and staged reservations, including on errors and panics. Other transactions and independent writes remain outside the queue and can still cause conflicts. A callback must not wait for another FIFO transaction on the same store; same-thread nested admission returns an error, but cross-thread dependency cycles cannot be detected. Slow or stalled callbacks delay later participants. The queue is not a bounded-response or global fairness guarantee.
- `CheckpointStore::transaction_until` accepts a monotonic deadline and conservative or read-set validation, with or without FIFO admission. It checks expiry before admission, after queue and state-lock waits, after the callback, and immediately before commit. FIFO admission removes expired waiters. `TimedTransactionError::DeadlineExceeded` means this transaction's staged changes were not submitted; `Operation` wraps callback and I/O errors, including an I/O timeout during commit whose outcome may be unknown. Transaction reads and staging started after expiry return `TimedOut`; a callback that forwards that error returns `Operation`. Callbacks, state-lock waits and I/O are not forcibly interrupted, and a commit already started can succeed after expiry. External callback side effects are not rolled back. Deadlines do not provide bounded completion.
- `CheckpointStore::snapshot` captures the current verified checkpoint block directory and bounded suffix overlay under the state read lock, sharing the read-only log handle and duplicating the checkpoint file descriptor. It does not copy the full base index or values. Its point, bounded bulk and ordered paginated reads use captured immutable log locations, including overlay tombstones, despite later mutations and checkpoint rollover. Reads hold the store's state read lock and fail if a prior write left the instance unusable; checkpoint blocks and values retain their existing checksums. One open store permits at most 16 active views, 262,144 copied block-directory entries, 65,536 copied overlay keys and 16 MiB of copied overlay-key bytes across them. Per-view block, overlay-key and key-byte limits can be lowered. Counts exclude allocator capacity, returned data, file buffers and total process memory. Creation errors and panics release reservations; `cancel` or drop releases the captured view before its reservation. A monotonic deadline rejects operations begun after expiry, but does not interrupt lock waits or I/O. A later snapshot request or explicit `reap_expired_snapshots` call reclaims expired idle views; in-progress reads are skipped. There is no background timer, so an expired view can retain resources until reaping, cancellation or drop. Snapshots borrow the store, do not survive reopening, and rely on the source log remaining append-only. They do not provide write transactions or safe live-log reclamation.
- `transaction_with_read_set` is an opt-in serializable mode using the same snapshot, writer barrier and atomic commit. When the generation changed, it compares each point read against the current index and compares every entire requested scan range, including entries beyond the returned page. Matching key membership and immutable log locations mean the transaction's snapshot observations still match the state at validation; its staged writes can then be serialized at that point. This reasoning depends on locations remaining immutable and not being reused while transactions exist; any future live compaction must preserve that property or introduce a validated version identity. Reads of a transaction's own staged entry need no base dependency. A present value changed and restored has a different location and conflicts. A previously absent key inserted and deleted before validation can return to the same absent state without a conflict; this is not an absence-version or change-notification guarantee. Changes outside the read dependencies may commit without conflict. Read dependencies are limited to 2,048 distinct point/range constraints and 2 MiB of key/bound bytes per transaction; failure is reported before returning an untracked read. Validation examines at most 65,536 point checks or pairs of range entries; exceeding that work limit returns an error without committing. Allocator overhead is excluded. Full-range validation holds the writer barrier and can be expensive. Reads through independent `Store` methods, callback side effects and other processes are not included. The existing conservative `transaction` semantics remain unchanged.
- `transaction_with_read_set_fifo` uses the same validation and commit rules with an optional FIFO admission queue after callbacks finish. A turn is released after the writer barrier is released, including on unwinding. The queue is limited to 16 entries and fails closed if poisoned. It orders only calls to this method; regular writes, other transaction modes, scheduling delays and I/O are outside that order. It does not promise a wait-time bound and may increase latency or conflict retries. Existing transaction methods do not use this queue.
- `transaction_until` accepts a monotonic deadline and a choice of conservative, read-set or read-set FIFO validation. It checks expiry before callback admission, after the callback, after acquiring the writer barrier and immediately before beginning commit; FIFO admission also removes expired waiters. The distinct `TimedTransactionError::DeadlineExceeded` is returned only before that transaction's staged batch is submitted. `TimedTransactionError::Operation` wraps callback, validation, admission and I/O errors; an I/O error of kind `TimedOut` during commit can have an unknown outcome and must not be treated as an engine-confirmed abort. A callback forwarding an expired snapshot read yields `Operation`. Callbacks, writer-lock waits and I/O are not interrupted; if expiry occurs after the final check, a commit can complete and succeed after the deadline. External callback side effects are not rolled back. Deadlines are not cancellation tokens or bounded-response guarantees.
- Concurrent transactions on one open store share a 64 MiB budget for encoded staged records, including each staged key, value, record header and checksum but excluding the per-batch count field. A reservation is acquired before a staged entry grows; if admission fails, that entry and all earlier staged changes remain unchanged. A callback can catch the error and continue, or propagate it to abort. Replacements that shrink release their excess reservation; transaction completion, callback error and unwinding release the remainder. The budget does not include allocator overhead, snapshots, returned values, commit encoding buffers, independent batches or other stores; it is not a total memory limit or fair scheduling guarantee.
- `Store::snapshot` copies one index view under the read lock and borrows the store until dropped; snapshot reads and paginated scans use those immutable log locations despite subsequent writes. It rejects requests over caller-supplied limits and hard per-snapshot caps of 16,384 keys and 4 MiB of key bytes. Per open store it also limits active snapshots to 16, aggregate copied keys to 65,536 and aggregate copied key bytes to 16 MiB. Reservations are released on drop and on unwinding during construction. Map overhead, returned values, multiple stores and total process memory are not covered by those counters. A poisoned store rejects new snapshot reads. Snapshots are process-local, cannot outlive the store, and do not provide write transactions or survive reopening. Old log locations remain available because the live log is append-only; there is no version garbage collection or automatic live-store compaction. The log grows without bound and its key index is held in memory. `compact_to` verifies the complete source log and its live index, writes only live records into a separate staging store, reopens and verifies it, and publishes it without replacing an existing path. It blocks mutations during copying but leaves the source and its readers intact; changes after it returns are absent from the copy. A failure syncing the destination parent after publication has an uncertain outcome. It does not bound memory, provide automatic switchover, or make historical data in the source or older backups disappear.
- A caller can explicitly cancel a read-only snapshot, which clears its copied index before releasing its reservation; cancellation is idempotent and subsequent reads return an error. `snapshot_until` provides an optional monotonic deadline: creation and new read/scan operations at or after expiry return `TimedOut`. An operation started before expiry can finish later; neither lock waits nor I/O are interrupted. A later snapshot request or explicit `reap_expired_snapshots` reclaims expired views without waiting for an in-progress read; busy views are skipped for a later attempt. The deadline registry is bounded to 16 entries; a new deadline snapshot can fail temporarily if stale entries are busy. There is no background timer, so an idle expired view can retain its reservation until reaping, cancellation or drop. Cancellation does not affect other snapshots or transactions, and a cancelled snapshot still borrows the store until dropped. There is no live-log reclamation.
- Ordinary `Store::compact_to` writes ordinary `DB01` records to a private staging store in groups of at most 64 records and 4 MiB encoded bytes, except that a single larger record forms its own group. Each group is synchronized with the target's applicable witness protocol. The target index is rebuilt by reopening, and the copy is checked against the source before non-overwriting publication. A copy or synchronization failure does not publish the staging directory; a parent-directory sync failure after publication has an uncertain outcome. This is not atomic switchover or live compaction, and the group size is not a total-memory quota.
- `CheckpointStore::compact_to` pauses source mutations, validates its trusted checkpoint and complete bounded suffix, then streams live keys into a new private store using the same synchronized record-group limits. It validates the target log and witness, compares its ordered key/value digest and count against the source, and emits a verified checkpoint inside the copy. The returned checkpoint digest must be protected separately. The compacted history starts with the current live keys, so its historical key-count peak is reset to that count. Existing readers may continue; the source remains unchanged, later source writes are absent from the copy, and switching applications is manual. A parent-directory sync failure after publication has an uncertain outcome. This avoids materializing complete source or target indexes during the operation but does not bound total process memory, provide in-place compaction, or erase old records from the source or backups.
- Backup, restore, upgrade, checkpoint and compaction reserve the `.emda-stage-v1-` destination-path namespace. New staging operations synchronize a versioned ownership marker and its parent directory before creating a payload, hold a nonblocking shared advisory lock on the destination parent during staging and publication, and release it after the operation finishes. A conflicting cleanup returns `WouldBlock`; if the lock cannot be acquired, a new staging operation fails before creating its marker. The explicit `cleanup_abandoned_staging` API takes the parent lock exclusively, recognizes matching markers and payload types, skips symlink payloads and unknown markers, and synchronizes the directory after attempted cleanup. Deletion may be partial if it reports an error. This requires a trusted directory and cooperating processes; it is not safe against concurrent external replacement, adversarial directories, unsupported locks, or uncooperative software. Cleanup is not automatic or secure erasure. Older unmarked `.db-*` files and directories are not removed and may contain plaintext data. Forked children can temporarily retain a lock after a killed parent; a normally dropped staging guard explicitly unlocks even if a descriptor was duplicated. Continuing an inherited staging operation after `fork` is unsupported.
- A `Store`, `CheckpointStore`, `CheckpointView`, `RecoveredCheckpointView` or borrowed snapshot may be used in its owning process. After `fork`, the child must not use the inherited object; it should `exec` or exit without running inherited database operations. On tested Linux, the long-lived advisory lock descriptor is inherited until `exec` or close, so dropping the original object can leave the store temporarily locked by a pre-exec child or another duplicated descriptor. The descriptor is close-on-exec for the tested ordinary process-spawn path; an independently executed contender is excluded while the original owner is alive. Manually changing descriptor flags, unlocking or passing inherited descriptors to other processes is unsupported. These are cooperative filesystem locks, not tenant isolation or fencing against noncooperating programs.
- Process-kill tests stop these five operations after staging and after publication before parent synchronization, check that cleanup is blocked while they run, and validate the source or published copy and cleanup on the running OS. Marker and cleanup directory-sync failures are also injected. These tests do not establish which entries survive physical power loss.
- SQL and document interfaces do not exist, so no atomicity or consistency guarantee across interfaces is currently available.

### Corruption and format compatibility

- Header and record CRC32 checks detect some accidental corruption on reopen; current value bytes are checked on read. CRC32 is not authentication, cannot detect every possible error, and cannot reconstruct damaged data. A detected checksum failure is reported; no automatic repair from replicas or backups exists. Backups add a length and SHA-256 digest and revalidate records, but are unencrypted, unauthenticated, and not proof of protection against all storage failures.
- Explicit `checkpoint_to` verifies the complete source log and live index, writes a checksummed index file without replacing an existing path, synchronizes it, and returns its SHA-256 digest only after parent-directory synchronization. A publication sync failure has an unknown outcome. `open_with_checkpoint` requires that digest from separately trusted metadata, verifies the checkpoint file, codec version, recorded historical key peak, witness boundary and complete covered log-prefix SHA-256, then replays and validates the tail. Optional log/key limits can be applied on open. A rejected checkpoint never authorizes partial recovery; ordinary `open` replays the full log without it. Checkpoints contain plaintext keys, are not independent backups, and are not authenticated if an attacker can replace both checkpoint and trusted digest. Prefix hashing still reads all covered log bytes and the index is loaded into memory; neither recovery time nor process memory is bounded by the checkpoint.
- `CheckpointView` provides a bounded-memory, historical read-only checkpoint view under a shared advisory lock. Cooperating writable stores cannot coexist with it; multiple views can. Opening verifies the trusted digest and full covered log prefix, and each subsequent index-block read is checked against a digest held in the view. Value reads verify their existing CRC. It does not replay or validate bytes after the checkpoint and can show older data; `has_log_tail` reports only the presence of such bytes at open, including potentially incomplete or corrupt records. It is not current recovery. At most 131,072 index blocks are indexed per view, and each block read uses at most a 32 KiB index buffer, in addition to the bounded result or value. Searches may read several blocks, especially when keys share long prefixes, and scans may read more. Aggregate memory across simultaneous views or calls is not limited. The separately trusted digest, cooperative-locking assumptions and complete prefix-hashing costs above apply equally here.
- `RecoveredCheckpointView` uses the same independently trusted checkpoint and shared lock, then validates and replays every record from the checkpoint boundary through the witnessed log boundary into an in-memory overlay. Point reads and ordered scans merge that overlay, including tombstones, with the verified checkpoint blocks. It rejects any bytes beyond the witness, including a complete unacknowledged tail; a writable store must adopt a valid complete tail before the view can open. Default hard limits are 64 MiB of raw suffix, 16,384 distinct touched keys and 4 MiB of their key bytes, including deleted keys; callers can choose lower limits. Limits are checked before a partial view is returned. The limits do not cover checkpoint block metadata, allocator overhead, record buffers, returned values, simultaneous views or total process memory. Opening still hashes the full covered log prefix, and neither recovery time nor aggregate memory is bounded. Later checkpoint block reads and selected values retain their checksums; noncooperating external modification is outside the locking model. The view cannot coexist with a cooperating writer and is not a writable disk-backed index.
- `CheckpointStore` uses the verified checkpoint and bounded recovered suffix as a writable base under an exclusive advisory store lock. Reads and mutations synchronize through one process-local lock. Bulk reads capture one state, preserve input order and duplicates, and enforce the same 1,024-key and 32 MiB response limits as the ordinary store; they are not transactions. Single-key changes, conditional updates, increments and blind atomic DB02 batches append in order, synchronize using the existing V2/V3 witness protocol, and publish their overlay changes only after successful synchronization. A batch is observed before or after its complete publication. Before append, admission checks suffix bytes and distinct touched keys/key bytes, including tombstones; callers may choose lower limits than the recovered view hard caps. A rejection leaves the log unchanged. After append starts, an error or panic makes its outcome uncertain and prevents further operations on that instance. Reopening validates the trusted checkpoint, the witnessed boundary and the complete suffix, subject to its limits; a complete unacknowledged tail is synchronized and its witness advanced before the instance is returned. An incomplete tail fails closed without truncation. A synchronization or witness error during recovery has an uncertain outcome. Tests inject partial appends and V2 witness writes, V3 metadata write/sync failures and panics, and kill a process after acknowledgement; these tests do not establish power-loss safety. Explicit `CheckpointStore::checkpoint_to` pauses mutations, revalidates the separately trusted base checkpoint and its covered log prefix, replays the witnessed suffix, checks the resulting overlay and historical key-count peak, and streams a new checkpoint. It validates the output before publishing it, synchronizes the staging file and parent directory, and returns a digest that must be protected separately. A publication sync error leaves the new path uncertain. `checkpoint_to` leaves the current overlay in place. `rollover_to` additionally opens and verifies the new checkpoint under the same exclusive lock, then swaps views and clears the overlay without a lock gap; both reads and writes wait during the operation. If publication succeeds but the new view cannot be opened, the old view stays active and the new path may exist. The caller must persist the returned digest and choose the checkpoint on the next open; this selection is not recorded automatically. Keep the store directory accessible at its resolved path during a live switch. If the new digest is lost, an older trusted checkpoint may be usable within its suffix limits; ordinary full-log recovery remains the fallback. The operation uses bounded block buffers, a second bounded suffix overlay and, during handoff, two checkpoint block directories; these limits are not a total process-memory guarantee. The full prefix is still hashed. `CheckpointStore::backup` holds a read barrier that blocks mutations while copying, verifying and publishing a full-log backup; other readers may proceed. Backup, restore and format upgrade validate every record through the streaming parser without constructing a full key index, but record and batch buffers, returned values and other allocations remain outside a total-memory quota. The backup remains plaintext, unauthenticated and dependent on independent retention and restore checks. This path has no group commit, automatic checkpoint rollover or total-memory quota. A suffix exceeding the configured caps needs a newer checkpoint or ordinary full-index recovery.
- `CheckpointStore::compare_exchange_batch` checks up to 1,024 point-value conditions under its exclusive in-process write lock and applies one atomic DB02 batch only when every condition matches. `None` denotes an absent key; duplicate conditions are checked independently. Condition keys and expected values are limited to 32 MiB in total. Mismatches and validation failures append nothing; an append or synchronization error has an unknown outcome and poisons the instance. Conditions compare current values and can miss an ABA change, and no range or phantom validation is provided. This primitive is not a general read-modify-write transaction callback.
- `CheckpointStore::rollover_managed` provides opt-in persistent selection under the same exclusive store lock. It verifies and durably publishes a new checkpoint, verifies the new view, writes and synchronizes a versioned selection in the store directory, atomically renames it over `checkpoint.selection`, and synchronizes that directory before switching the live view or resuming reads and writes. A checkpoint-stage failure keeps the previous view; if selection publication fails or panics, the writer becomes unusable because the rename may have occurred. `open_managed` acquires the store lock, rejects missing, malformed, unknown-version or symlink selections, verifies the referenced checkpoint and complete covered log prefix, and synchronizes the visible selection and directory before accepting writes; complete unacknowledged tails are subject to the existing validation and limits. If the first selection was never published, explicit recovery with the prior trusted checkpoint or ordinary full-log recovery is required. The selection records an absolute path; moving or deleting the checkpoint breaks reopening. Its SHA-256 is only an accidental-corruption check: the store directory and selection must be trusted and protected separately from checkpoint contents, and an attacker who can replace both can forge them. External modification or noncooperating access is unsupported. Once a selection exists, explicit `CheckpointStore::open` and unmanaged live rollover reject it. Ordinary `Store` and older engine revisions do not enforce this selection and may grow a suffix beyond managed limits. Backup/restore preserves the log but not this selection or its checkpoint. This is not automatic scheduling, in-place compaction, log reclamation, a memory quota or a physical power-loss guarantee. Injected pre/post-rename errors and panics, competing writer barriers, corruption, and process kills before/after rename are tested on the running OS.
- `CheckpointStore::rebuild_managed_selection` explicitly recovers an existing witnessed store using the ordinary full-log replay and in-memory index, under its exclusive advisory store lock. It rejects invalid, symlink or unknown-version selection metadata, builds a non-overwriting checkpoint, opens it as a managed-compatible view under the same lock, and atomically publishes and synchronizes a fresh selection. It does not need the previous checkpoint to be accessible and can repair a suffix that exceeds the managed reader's limits. If checkpoint publication fails, the old selection is untouched; an error or panic during selection publication can leave either selection visible. Reopen and verify the visible selection, or use full-log recovery when no selection is present. The method releases its lock before returning; callers must coordinate other writers before reopening. It loads the complete in-memory index, may allocate an additional verification index, hashes the full log, and provides no bound on time or total memory. It is not log compaction or automatic recovery. Fault, lock-exclusion and process-kill tests cover these boundaries only on the running OS.
- `CheckpointStore::open_with_resource_limits` accepts an optional per-open cap on the entire log file, including its header, replaced records and tombstones. It rejects an oversized log before suffix replay or adoption and rejects a mutation before append if its encoded record would exceed the cap. Its write lock serializes admission and commit, including across checkpoint rollover, which does not reclaim log bytes. The cap is not persisted and excludes checkpoint files, backups, memory and total project storage.
- Single-key records use the experimental `DB01` marker; atomic batches use the `DB02` marker and contain checksummed `DB01` records. Older revisions cannot reopen logs containing `DB02`. On Linux filesystems supporting user xattrs, new stores have a checksummed `EMDALOG3` header, a metadata witness, and an immutable `commit.state` identity anchor. Unsupported xattr operations during creation fall back to V2 (`EMDALOG2` and its changing `commit.state` witness); other initialization errors propagate. Existing V2 stores retain their two-sync protocol and existing unwrapped `DB01` logs retain their earlier recovery limitations. Opening V3 never falls back if required metadata is missing or unsupported. Backups retain the log format and length/digest; restore recreates and synchronizes the format's witness. V3 restore currently requires Linux with supported xattrs. Ordinary file-copy tools must preserve xattrs, identity files and log bytes; use the engine backup/restore API for verified copies. Unknown or invalid markers are rejected. Older engines cannot open the new header. The software version and on-disk format version are separate; the current prototype has no stable backward-compatibility or downgrade promise. See [VERSIONING.md](VERSIONING.md).

## Proposed contract for future design

The following are acceptance targets, not existing guarantees. Exact algorithms and API behavior must be specified, reviewed, and tested before release.

1. **Durability:** Define the exact acknowledgement point, storage and filesystem assumptions, crash and power-failure model, partial I/O behavior, and how an unknown result is reported. Acknowledged writes must survive the documented failures under those assumptions; failed requests must never be silently treated as definitely absent. Backups and restores require separate verification.
2. **Transaction isolation:** Document every supported level and its anomalies. The prototype provides an optimistic serializable transaction API within one open store; broader production semantics and additional isolation levels require further validation and design. If offered, serializable transactions must prevent dirty reads, non-repeatable reads, phantoms, and write skew. Serializability alone must not be described as a real-time ordering guarantee.
3. **Cross-interface atomicity:** Within a single supported transaction and database, key-value, document, and SQL operations must use the same commit and isolation machinery. Record and index updates commit together or not at all. Cross-database, cross-project, external service, and distributed transaction behavior must be specified separately; no guarantee is assumed.
4. **Ordering and consistency:** Define operation and commit order, read-your-writes, concurrent conflict behavior, and what a client may observe during and after failure. For streams and replication, define the scope of ordering, acknowledgement, retry, and delivery semantics explicitly.
5. **Snapshots and garbage collection:** Define snapshot visibility, lifetime, resource limits, cancellation/expiry behavior, and how retained versions are reclaimed. Compaction and garbage collection must not invalidate an active supported snapshot or remove data needed for recovery. Any timeout must be explicit rather than silently changing a result.
6. **Corruption:** Specify which corruption is detected, when the engine stops safely, and how recovery from a verified backup or replica works. Checksums alone must never be presented as data recovery.
7. **Formats:** Version record, index, checkpoint, snapshot, API, and protocol formats independently where appropriate. Define supported upgrades, downgrades, migration and rollback, and fail safely for unknown versions. Compatibility claims require tests using persistent fixtures from the supported versions.
8. **Sleep and wake:** Stopping an idle project worker must not weaken this contract. Define draining of in-flight operations, snapshots and background jobs, durable stored data, ownership fencing, bounded wake-up retries, and recovery errors. No scale-to-zero behavior is implemented today; see [SCALE_TO_ZERO.md](SCALE_TO_ZERO.md).
9. **Project boundaries:** Transactions, caches, indexes, snapshots, logs, streams, and recovery must not access another project's data without explicit authorization. Enforce and test this in the service, engine, and storage layers; see [PROJECT_ISOLATION.md](PROJECT_ISOLATION.md). No tenant security is implemented today.

## Evidence required before a guarantee is advertised

Deterministic partial-append including every byte of a vectored group, partial witness writes at every byte, witness update/sync errors, ordering of log and witness syncs, directory-creation ancestor-sync errors, short-read errors including during buffered replay, record-boundary truncation and byte-by-byte log/witness corruption checks, a torn-witness crash model, controlled overlapping reads and writes, reservation failure and panic tests, grouped-sync failure and panic tests, delayed-handoff and queue-limit tests, short model-checked single- and multi-key histories of independent operations, 2,048 short mixed transaction/batch/read histories checked against a serial model with reopening after each history, process termination after acknowledged concurrent writes, persistent legacy, V2 and V3 fixtures, legacy upgrade, backup/restore checks, and a local cross-filesystem restore drill exist. Backup checks include every truncation and single-byte mutation position of a small fixture, competing restores to one destination, and an existing symlink destination. The V3 path additionally has every-byte record/witness corruption, every shorter log length, all prefixes of an interrupted append crossed with torn witness prefixes, log-only rollback, delayed-sync publication, metadata failure/panic, upgrade, and restored-boundary tests. Coverage-guided fuzz campaigns exercise malformed recovery input. Further work must exercise interruption at every initialization/commit/backup boundary, the remaining directory-sync paths and actual power-loss models, off-host restore drills, broader model-based concurrent histories, and additional persistent compatibility fixtures. A process kill alone is insufficient for power-loss claims. Snapshot, compaction, index, and cross-interface tests must be added as those features are implemented. Report the assumptions and any untested failure cases alongside the results.
