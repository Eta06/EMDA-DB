# Direct mutation outcomes

Revision `856a9f6e52169a21fb07268176270321a72609ea` adds opt-in `MutationFailure` outcomes to direct puts, deletes, compare-exchange, integer increments and atomic blind batches on both writable stores, and conditional batches on the checkpoint-backed store. `Rejected` says only that this call was not submitted; it does not prove the store is healthy or resolve an earlier uncertain write. `OutcomeUnknown` means the mutation may have been submitted and needs reconciliation before retry. Ordinary coordinator failures can be classified as unknown even before append. Automatic checkpoint maintenance can have independent effects; panics unwind without this enum. Existing APIs retain their error types.

Focused V2/V3 fault tests check every new operation against append or synchronization failures and witness errors. Partial records remain preserved and fail closed on reopening. A concurrent one-key quota race passed 25 repetitions on each writable path; one writer succeeded and the other was rejected without exceeding the cap.

## Concurrent failures and recovery

The [EAGAIN](../benchmarks/results/2026-11-14-mutation-eagain.json.gz), [EIO](../benchmarks/results/2026-11-14-mutation-eio.json.gz) and [EINTR](../benchmarks/results/2026-11-14-mutation-eintr.json.gz) reports cover 160 selected concurrent direct-write syscall-injection cases across V2/V3, both writable paths and both recovery orders. EAGAIN produced 80 observed acknowledgements, 96 confirmed rejections and 160 unknown outcomes, of which 95 were present after recovery. EIO produced 77 acknowledgements, 96 confirmed rejections and 160 unknown outcomes, of which 97 were present. Every confirmed rejection stayed absent. EINTR was retried in the sampled cases, with 8,192 writes acknowledged. A further [32-case transaction EAGAIN check](../benchmarks/results/2026-11-14-mutation-transaction-eagain.json.gz) covers the existing detailed transaction path after this refactor. Verify each report with `scripts/verify_concurrent_eio_results.py`.

Ten local repetitions of each concurrent process-kill workload produced [320 cases](../benchmarks/results/2026-11-14-mutation-kill.json.gz), alternating existing and detailed direct writes. Both recovery paths reopened all cases. The independent-write cases checked 6,760 individual observed acknowledgements. The update/delete cases observed 10,705 acknowledgements, including 3,348 deletes, and checked each worker's latest acknowledged or in-flight state; 544 in-flight operations were observed. The [mixed-operation history run](../benchmarks/results/2026-11-14-mutation-mixed-history.log.gz) checked 4,096 histories across V2/V3 and both writable paths. All are finite samples with the operating system still running, not physical power-loss tests.

The stable, Rust 1.85 and optimized all-target suites each passed 957 tests, with the test harness limited to four threads; both all-target Clippy checks passed. The script suite passed 127 tests. An [initial stable build](../benchmarks/results/2026-11-14-mutation-initial-build-failure.log.gz) failed because a read-only process-kill test model lacked the newly added test-adapter methods. Those methods were added and the suites reran successfully.

## Local performance

The [log-capped](../benchmarks/results/2026-11-14-mutation-direct-log.json.gz) and [key-byte-capped](../benchmarks/results/2026-11-14-mutation-direct-key.json.gz) comparisons used separately built baseline `0158359cbc690df1a8144800a8ff966c6e2bd8e0` and candidate binaries on the same shared Linux VM. Each report contains 48 rotated-order runs with one or four clients, 50% or 100% writes, 200 operations per client and fresh fixtures. These measure the existing direct API, use synchronized writes and verify sampled values after reopening; they do not directly measure the new detailed method's overhead.

In the four-client 50%-write log-capped case, median write p50 was 340.1 versus 348.1 µs and throughput was 20,264 versus 20,030 operations/s. The equivalent key-byte-capped case measured 336.4 versus 350.1 µs and 20,361 versus 19,937 operations/s. Other cases moved in both directions. The log and key-byte comparisons observed up to 5.56% and 6.25% VM steal and up to 16.67% and 18.18% I/O wait, respectively, with no cgroup throttling observed. Telemetry covers the whole VM/cgroup including the workload. These short, warm-cache samples do not establish a general regression, improvement or competitor ranking.
