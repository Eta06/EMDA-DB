# Compound range comparison, 2026-11-04

The planner can use a compound index for an equality prefix followed by a scalar range when every later indexed field is proven present. We compared that path with the prototype's full scan, SQLite 3.49.1, PostgreSQL 18.6 and MongoDB 8.0.34. Each query selected a tenant value and numeric lower bound, returned ID-ordered documents, and checked the complete result against the same expected data. Some nonmatching rows shared the tenant value. Each run also reopened the local stores or reconnected to each server and checked all stored documents; this was not a server-crash or restore test.

Each series used four fresh data sets per case, one client, 10 warmup and 50 timed iterations per variant. Values are microseconds: the median of four run medians, with the range of those medians in parentheses. PostgreSQL and MongoDB use Python drivers and loopback containers; the prototype and SQLite run in-process in Rust. These adapter and transport differences are included in the timings.

SQLite had the lower indexed median in these cases. The prototype's planned median was below the PostgreSQL and MongoDB loopback adapter medians, which include network and Python-driver work; this does not establish that its storage engine is generally faster. PostgreSQL and MongoDB varied substantially between runs. This workload uses only present integer and string fields, small hot data sets and read-only timed queries. It does not measure concurrency, write throughput, cold starts, project isolation, total per-engine memory, physical power loss or off-host recovery.

The prototype validates stored documents and index entries; SQLite filters JSON text and the Rust adapter decodes returned JSON. PostgreSQL stores JSONB and uses a checked bitmap-index plan after disabling sequential, ordinary index and index-only scans. MongoDB stores BSON and uses a hinted compound index. SQLite's forced plan reports an index search and a temporary B-tree for ID ordering; the checked PostgreSQL and MongoDB plans also sort results. Their SQL/JSON/BSON semantics, features, durability and resource allocations differ. Prototype writes use the synchronized witnessed store; SQLite uses WAL and `synchronous=FULL`; PostgreSQL uses `fsync`, `synchronous_commit` and `full_page_writes`; MongoDB setup writes use `w=1, j=true`.

All 72 pre-run quiet checks passed. Across process windows, primary VM steal reached 7.14% and I/O wait 6.67%; the repeat reached 4.55% and 6.67%. No cgroup throttling or direct reclaim was recorded. These VM/cgroup observations include setup and verification and are not per-engine resource measurements. The VM had a four-CPU quota, pinned driver and server CPU sets, and an overlay filesystem; the host, backing device and cache state were not independently controlled.
